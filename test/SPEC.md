# 용어 추출 서비스 — 구현 명세

> 유비쿼터스 언어(공통 용어) 사전 생성 툴의 **AI 서비스** 파트.
> 이 문서 하나로 구현이 가능해야 한다. 모르는 것이 있으면 추측하지 말고 §10 결정 기록에 적어라.
>
> **최종 갱신 2026-09-07** — 골드셋 25개 확장 · VARIANT 편집거리 제거(§4 · §10 D-1) 반영본.

---

## 1. 제품 맥락 — 왜 이게 필요한가

팀이 각자 쓴 문서를 보면 **같은 뜻을 다른 말로 부르는 지점**(회원 / User / 고객)과 **같은 말을 다른 뜻으로 쓰는 지점**("주문"이 장바구니인가 결제 확정 건인가)이 있다. 이걸 사람이 찾으려면 문서를 다 읽어야 한다.

이 서비스는 **문서 여러 개를 받아 그런 지점을 후보로 뽑아준다.** 확정은 사람이 한다 — 이 서비스는 "이것들이 같은 말인 것 같다"까지만 하고, 대표어와 정의를 정하는 것은 사람의 몫이다.

**정밀도가 재현율보다 중요하다.** 오탐이 쌓이면 사람이 기능 자체를 무시한다. 놓친 것은 사람이 나중에 추가할 수 있지만, 틀린 제안이 쏟아지면 화면을 안 보게 된다.

---

## 2. 이 리포가 하는 것 / 하지 않는 것

**한다**
- 문서 N개를 받아 용어 후보를 뽑아 JSON으로 반환
- 후보를 4종으로 분류: 표기 변형 · 동의어 · 동형이의 · (동음이의는 범위 밖)
- 각 후보가 어느 문서 어느 위치에서 나왔는지 오프셋과 함께 반환
- 이미 사전집에 등재된 용어는 후보에서 제외

**하지 않는다**
- DB 접근 (모든 입력은 요청 본문으로 들어온다)
- 인증·인가 (Spring Boot가 앞단에서 처리)
- Kafka 소비·발행 (Spring Boot가 이 서비스를 HTTP로 부른다)
- 사용자 화면
- 사전집 저장 (후보를 반환만 하고 상태를 갖지 않는다 — **stateless**)

## 3. 계약

### 3.1 요청

```
POST /extract
Content-Type: application/json
```

```json
{
  "jobId": "0f2c1a3e-...",
  "workspaceId": "9b7d...",
  "dictionaryVersionNo": 7,
  "existingTerms": [
    {
      "termId": "t-001",
      "preferredForm": "구독자",
      "englishName": "Subscriber",
      "synonyms": ["이용자", "타겟 유저", "User"]
    }
  ],
  "documents": [
    {
      "documentId": "d-001",
      "title": "커머스 기획안",
      "department": "기획",
      "content": "문서 전문 ..."
    }
  ]
}
```

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `jobId` | string(uuid) | O | 응답에 그대로 반환. 로그 상관관계용 |
| `workspaceId` | string(uuid) | O | 로그용. 판정에는 쓰지 않는다 |
| `dictionaryVersionNo` | int | O | 어느 리비전 기준으로 뽑았는지 재현성 확보용 |
| `existingTerms` | array | O | 빈 배열 가능(첫 추출). **여기 있는 표기는 후보로 내지 않는다** |
| `documents` | array | O | 1개 이상. `content`는 마크다운 또는 평문 |

**`kinds`는 요청에 없다.** 한 번에 전부 뽑고, 어떤 종류를 보여줄지는 화면에서 거른다.

### 3.2 응답

```json
{
  "jobId": "0f2c1a3e-...",
  "status": "SUCCESS",
  "dictionaryVersionNo": 7,
  "candidates": [ /* 아래 두 형태 중 하나 */ ],
  "usage": {
    "model": "gemini-...",
    "inputTokens": 18422,
    "outputTokens": 2104,
    "llmCalls": 2,
    "elapsedMs": 24310
  },
  "warnings": []
}
```

`status`: `SUCCESS` | `PARTIAL` | `FAILED`
- `PARTIAL` — 일부 종류만 성공. `warnings`에 사유를 넣는다
- `FAILED` — `candidates`는 빈 배열, `warnings`에 사유

### 3.3 후보 — 그룹형 (`VARIANT` · `SYNONYM`)

여러 표기가 **하나의 개념**을 가리키는 경우.

```json
{
  "candidateId": "c-1",
  "kind": "SYNONYM",
  "forms": ["이용 보류", "휴면 전환", "suspend_account"],
  "proposedPreferredForm": "구독 일시정지",
  "proposedEnglishName": "SubscriptionPause",
  "proposedDefinition": "구독을 해지하지 않고 일시적으로 중단한 상태",
  "confidence": 0.82,
  "reason": "세 표현이 모두 구독 상태를 유지한 채 이용만 중단하는 것을 가리킨다",
  "occurrenceCount": 23,
  "documentCount": 5,
  "occurrences": [
    {
      "documentId": "d-001",
      "department": "기획",
      "form": "이용 보류",
      "snippet": "결제 실패가 3회 누적되면 계정을 이용 보류 상태로 전환한다",
      "charStart": 412,
      "charEnd": 417
    }
  ]
}
```

### 3.4 후보 — 갈래형 (`HOMOGRAPH`)

**하나의 표기가 여러 뜻**으로 쓰이는 경우. 이것이 이 제품의 핵심 장면이다.

```json
{
  "candidateId": "c-9",
  "kind": "HOMOGRAPH",
  "forms": ["주문"],
  "confidence": 0.91,
  "reason": "기획 문서는 장바구니에 담긴 시점을, 개발 문서는 결제 승인 이후를 주문이라 부른다",
  "occurrenceCount": 47,
  "documentCount": 9,
  "senses": [
    {
      "label": "장바구니에 담긴 상태",
      "definition": "구매 의사만 표시되고 결제가 이뤄지지 않은 건",
      "occurrences": [ /* 위와 같은 구조 */ ]
    },
    {
      "label": "결제가 완료된 확정 건",
      "definition": "결제 승인이 끝나 이행 대상이 된 건",
      "occurrences": [ /* ... */ ]
    }
  ]
}
```

- `senses`는 **2개 이상**이어야 한다. 1개면 동형이의가 아니므로 후보로 내지 않는다
- 갈래형에는 `proposedPreferredForm`·`proposedDefinition`이 없다 — 사람이 갈래마다 정해야 한다

### 3.5 필드 규칙

| 필드 | 규칙 |
|---|---|
| `candidateId` | 응답 내에서만 유일하면 된다. `c-1`, `c-2` 형태로 순번 |
| `kind` | `VARIANT` \| `SYNONYM` \| `HOMOGRAPH` |
| `forms` | 문서에 **실제로 나타난 표기 그대로**. 정규화한 형태를 넣지 않는다 |
| `proposedPreferredForm` | `forms` 중 하나이거나 새로 만든 말. 사전집에 이미 있는 표준어와 겹치면 안 된다 |
| `proposedEnglishName` | PascalCase. 코드·DB 네이밍에 쓰인다. 확신이 없으면 `null` |
| `confidence` | 0.0~1.0. **0.5 미만은 응답에 넣지 않는다** |
| `reason` | 한 문장. 화면에 그대로 보인다 |
| `charStart` / `charEnd` | 해당 문서 `content` 문자열의 인덱스(0-based, end 미포함). **UTF-16이 아니라 파이썬 문자 인덱스** |
| `snippet` | 해당 출현을 포함한 한 문장. 앞뒤 30자를 넘기지 않는다 |
| `occurrenceCount` | 전체 출현 횟수 (occurrences 배열 길이와 다를 수 있다 — 배열은 최대 5개만 담는다) |

**`charStart`/`charEnd`는 반드시 맞아야 한다.** Spring 쪽에서 이 값으로 문서 본문에 파란 글씨를 칠하기 때문에, 한 글자만 어긋나도 엉뚱한 데 표시된다. §7의 검증 스크립트가 이걸 확인한다.

### 3.6 그 외 엔드포인트

```
GET /health   →  {"status":"ok","model":"..."}
```

## 4. 판정 기준 — 무엇을 무엇으로 분류하나

| kind | 정의 | 예시 | 판정 방법 |
|---|---|---|---|
| `VARIANT` | 같은 말을 다르게 적음 | 로그인 / 로그 인 / login | **규칙** (LLM 없이) |
| `SYNONYM` | 같은 개념을 다른 말로 부름 | 이용 보류 / 휴면 전환 / suspend_account | LLM |
| `HOMOGRAPH` | **하나의 표기**가 문서마다 다른 뜻 | 주문 = 장바구니 vs 확정 건 | LLM (문맥) |
| ~~`HOMONYM`~~ | 형태만 같은 다른 단어 (주문注文/주문呪文) | — | **범위 밖.** 국어사전 대조가 필요한데 그건 다음 단계다 |

### 묶으면 안 되는 것 — 프롬프트에 반드시 넣을 것

1. **조건이 다르면 다른 개념이다.** "결제 취소"(결제 승인 전 철회)와 "환불"(결제 후 반환)은 동의어가 아니다
2. **상위·하위 관계는 동의어가 아니다.** "결제"와 "결제 수단"은 다르다
3. **역할이 다르면 다른 개념이다.** "관리자"(시스템 권한)와 "운영자"(고객 응대 담당)는 다르다
4. **이미 사전에 등재된 표기는 후보로 내지 않는다.** `existingTerms`의 `preferredForm`과 `synonyms` 전부

### VARIANT 규칙 (LLM을 쓰지 않는다)

**정규화 결과가 정확히 같을 때만 같은 그룹이다. 편집거리는 쓰지 않는다.**

```
정규화:  공백 제거 → 하이픈·언더스코어 제거 → 소문자화
        → 조사 제거 (은/는/이/가/을/를/의/에/로/으로)
          단 조사를 떼어 길이가 2 미만이 되면 떼지 않는다

비교  :  정규화 결과가 문자열로 같으면 그룹. 그 외에는 그룹이 아니다
```

| 예 | 정규화 결과 | 판정 |
|---|---|---|
| `로그인` / `로그 인` | `로그인` / `로그인` | **그룹** |
| `결제 수단` / `결제수단` | `결제수단` / `결제수단` | **그룹** |
| `회원 가입` / `회원가입` | `회원가입` / `회원가입` | **그룹** |
| `e-mail` / `email` / `E-Mail` | `email` 세 개 | **그룹** |
| `결제일` / `결제월` | `결제일` / `결제월` | **그룹 아님** |
| `login` / `로그인` | `login` / `로그인` | **그룹 아님** — SYNONYM으로 LLM이 잡아야 한다 |

> **편집거리를 뺀 이유.** 처음에는 "정규화 후 Levenshtein 거리 ≤ 1 이고 길이 ≥ 3"을 함께 두었는데, 골드셋의 `N9`(결제일 / 결제월)이 그 조건에 정확히 걸려 **오탐이 났다.** 한국어는 한 음절 차이로 뜻이 완전히 달라지는 경우가 흔해서 편집거리가 표기 변형의 근거가 되지 못한다. 골드셋 정답 네 개(`G4` `G5` `G12` `G13`)는 모두 정규화만으로 잡히므로 편집거리가 필요하지 않다.
>
> 오타(`로그인` / `로그읜`)는 잡지 못하지만, 그것은 표기 변형이 아니라 오타이고 잡으려 들면 오탐이 늘어난다. MVP 범위 밖이다.

## 5. 파이프라인

```
① 문서 정규화·문장 분할        문자 오프셋 보존
② VARIANT 추출 (규칙)          LLM 없음
③ SYNONYM + HOMOGRAPH (LLM)   문서 전문을 한 컨텍스트에 넣고 1회 호출
④ 후처리                       existingTerms 제외 · confidence 필터 · 오프셋 검증
⑤ 응답 조립
```

### ③에 대한 중요한 결정

**임베딩 클러스터링을 넣지 않는다.** 원 설계에는 "임베딩으로 후보를 묶고 클러스터별로 LLM을 부른다"가 있었는데, 그건 후보가 수백 개일 때 O(n²)를 막는 장치다. 현재 규모(문서 5장 · 합계 8,200자 안팎 · 대략 4~5천 토큰)에서는 **문서 전문을 한 컨텍스트에 넣고 한 번 부르는 쪽이 더 정확하고 싸다.**

**형태소 분석기도 넣지 않는다.** 후보 생성을 LLM에 맡긴다. 재현율이 부족하다는 것이 채점으로 확인된 뒤에 `kiwipiepy`로 명사구를 보강한다.

이 둘은 **채점 결과가 근거를 만들기 전에는 넣지 마라.** 넣는 데 하루가 들고 튜닝할 시간이 사라진다.

### 문서가 많아지면

문서 총량이 컨텍스트 한계에 가까워지면(대략 입력 20만 토큰 이상) 부서별로 나눠 호출하고 결과를 병합한다. **그때 가서 필요하면 하고, 지금은 하지 않는다.**

## 6. Gemini 호출 규칙

### 반드시 지킬 것

| | |
|---|---|
| **JSON Schema 강제** | `response_mime_type: "application/json"` + `response_schema`. 파싱 실패로 시간 날리지 마라 |
| **`temperature` 0~0.2** | 판정 작업이라 창의성이 필요 없다. **같은 입력에 같은 출력이 나와야 프롬프트 튜닝이 가능하다** |
| **응답 캐시** | `sha256(프롬프트 + 입력)` → `.cache/{hash}.json`. 후처리·채점 코드를 고칠 때 API를 다시 부르지 않는다. `--no-cache`로 무시 가능 |
| **호출 카운터** | 한 프로세스에서 20회를 넘으면 중단하고 에러. 루프 사고로 요금이 나가는 것을 막는다 |
| **재시도** | 5xx·타임아웃만 2회까지, 지수 백오프. 4xx는 재시도하지 않는다 |
| **API 키 폴백** | 여러 키(`GEMINI_API_KEY_1`, `_2`, ...)를 등록하면 1번부터 순서대로 쓰다가, 그 키 자체의 문제(401/403 인증 실패, 429 쿼터 소진)로 막히면 다음 키로 넘어간다. "같은 키로 재시도"가 아니라 "다른 키로 폴백"이라 위 재시도 규칙과 충돌하지 않는다. 키가 1개(`GEMINI_API_KEY`)뿐이면 기존과 동일하게 동작한다(§10 D-38) |
| **모델 폴백** | 체인은 두 경로. (1) `--model`에 콤마로 나열(예: `gemini-3.5-flash,gemini-3.6-flash`) — 명시한 순간 아래 `.env` 체인은 무시되고 이것만 쓴다(§10 D-39). (2) `--model` 없이 실행 — `.env`의 `GEMINI_MODEL_1`, `_2`, ...(없으면 단수 `GEMINI_MODEL`)를 자동으로 체인으로 쓴다(§10 D-40). 어느 경로든: 1번 모델부터 시도하다가 등록된 키를 전부 써도(429/401/403, 위 키 폴백 다 소진) **또는 5xx 과부하로 키를 전부 써도** 그 모델을 못 쓰면 다음 모델로 넘어간다 — 5xx도 키를 갈아보는 건 D-40에서 고친 것(키가 다른 프로젝트/쿼터일 수 있어 "5xx는 키 무관"이라 단정할 수 없다). 모델이 바뀌면 키 폴백은 1번 키부터 다시 시작한다. 체인 길이가 1이면(콤마 없는 단일 `--model`, 또는 `.env`에 번호 없이 단수만) 폴백 없이 정확히 그 모델만 쓴다 — 재현성 테스트에 영향 없음 |

### 모델 선택

**콘솔에서 현재 사용 가능한 모델 목록을 확인하고 고른다.** 긴 컨텍스트 + 저비용 계열. 고른 모델명과 이유를 `SPEC.md`의 §10에 적어라. 하드코딩하지 말고 환경변수 `GEMINI_MODEL`로 뺀다.

### 프롬프트 구조 — 네 덩어리로 나눠 파일로 관리

```
prompts/
  01_role.md        판정 기준 — 무엇이 동의어이고 무엇이 아닌가
  02_forbidden.md   묶으면 안 되는 것 (§4의 4개 규칙 + 채점하며 추가)
```

## 7. CLI — HTTP보다 먼저 만든다

처음부터 FastAPI로 짜면 디버깅이 느려진다. **CLI를 먼저 만들고 마지막에 감싼다.**

```bash
# 추출 실행
python -m app.cli extract \
  --fixtures fixtures/ \
  --out out/result.json

# 채점
python -m app.cli score \
  --result out/result.json \
  --gold fixtures/gold.csv

# 오프셋 검증 — charStart/charEnd가 실제 본문과 맞는지
python -m app.cli verify-offsets \
  --result out/result.json \
  --fixtures fixtures/
```

`extract`는 `fixtures/workspace.json`과 `fixtures/docs/*.md`를 읽어 §3.1 형태의 요청을 조립한 뒤, 서비스 함수를 직접 호출한다. HTTP를 거치지 않는다.

### 채점 출력

```
=== 그룹형 (VARIANT · SYNONYM) ===
완전 일치   4 / 5     G1 G3 G4 G5
부분 일치   1 / 5     G2  (누락: "이탈")
누락        0 / 5
오탐        2         "결제 취소+환불"  "결제+결제 수단"

정밀도  0.67   (합격선 0.70)   ✗
재현율  0.90

=== 갈래형 (HOMOGRAPH) ===
완전 일치   1 / 2     G6
누락        1 / 2     G7 ("활성")
```

**부분 일치를 따로 세는 것이 중요하다.** "이용자 / User"는 맞췄는데 "타겟 유저"를 빠뜨린 것은 완전 실패가 아니다 — 사람이 리뷰 화면에서 추가하면 된다.

## 8. 수용 기준 — 각 단계가 "됐다"의 정의

단계를 건너뛰지 마라. **앞 단계의 기준을 통과하지 못한 채 다음 단계로 가면 무엇이 원인인지 알 수 없게 된다.**

| # | 단계 | 통과 조건 |
|---|---|---|
| **1** | 계약 목킹 | `POST /extract`가 고정 JSON을 반환한다. 스키마가 §3과 일치한다 |
| **2** | 문서 파싱 | `verify-offsets`가 전부 통과. 임의로 고른 출현 5개의 `snippet`이 원문과 글자 단위로 일치 |
| **3** | VARIANT | 골드셋 `G4` `G5` `G12` `G13`을 LLM 없이 찾고, **`N9`(결제일/결제월)를 묶지 않는다.** 오탐 0 |
| **4** | SYNONYM | 정밀도 **0.70 이상**. 재현율은 참고만 |
| **5** | HOMOGRAPH | 골드셋 `G6`("주문")을 찾고 `senses`가 2개다 — **데모 핵심이라 필수.** `G7` `G14` `G15`는 참고 지표 |
| **6** | FastAPI | CLI와 같은 결과를 HTTP로 반환. `/health` 동작 |

### 정밀도가 0.70에 못 미치면

프롬프트 `02_forbidden.md`에 규칙을 추가하고 다시 채점한다. 세 번 시도해도 못 넘으면 **`confidence` 임계값을 0.5에서 0.7로 올려** 재현율을 희생하고 정밀도를 확보한다. 그래도 안 되면 그 사실을 그대로 보고하라 — 제품 설계에 "정밀도 0.7 미만이면 대조를 필수가 아니라 경고로 내린다"는 후퇴선이 이미 준비돼 있다.

## 9b. 골드셋 파일 형식

`fixtures/gold.csv`의 헤더는 아래와 같다. 파서를 이 헤더에 맞춰라.

```
id,kind,forms,preferred_form_hint,english_hint,trap_type,note
```

| 컬럼 | 뜻 |
|---|---|
| `id` | `G*` = 찾아야 하는 것 · `N*` = 찾으면 오답 |
| `kind` | `SYNONYM` / `VARIANT` / `HOMOGRAPH` / `NEGATIVE` |
| `forms` | `\|`로 구분된 표기들 |
| `preferred_form_hint` | 대표어 제안이 이 근처면 좋다. 완전 일치를 요구하지 않는다 |
| `english_hint` | 같은 성격의 참고값 |
| `trap_type` | 함정(`N*`)의 유형. 조건이 다름 / 역할이 다름 / 상위-하위 / 이미 등재 / 대상이 다름 / 주체가 다름 / 편집거리 함정 / 절차가 다름 |
| `note` | 왜 정답 또는 함정인지 |

> ⚠️ **`trap_type`은 이전 판의 `must_appear_in`을 대체한 컬럼이다.** 파서가 `must_appear_in`을 읽고 있으면 고쳐라.

## 10. 결정 기록

> 판단이 필요했던 것과 그 결론을 시간순으로 남긴다. 추측으로 넘어가지 말고 여기에 적어라.
> 아래 D-1이 형식의 예시다 — **무엇이 문제였고 / 무엇을 바꿨고 / 왜 그렇게 정했는가** 세 줄이면 충분하다.

### D-1 · VARIANT 판정에서 편집거리를 제거 — 2026-09-07

**무엇이 문제였나.** 초기 규칙은 *"정규화 결과가 같거나, 또는 정규화 후 Levenshtein 거리 ≤ 1 이고 길이 ≥ 3"* 이었다. 골드셋을 25개로 확장하면서 함정 `N9`(**결제일 / 결제월**)를 넣었는데, 이 둘이 편집거리 조건에 정확히 걸려 **같은 표기 변형으로 잘못 묶였다.** 정규화 후 `결제일` / `결제월`은 거리 1, 길이 3이다.

**무엇을 바꿨나.** 편집거리 조건을 **삭제**하고 *"정규화 결과가 문자열로 같을 때만 그룹"* 으로 좁혔다. 조사 제거에는 안전장치를 더했다 — **떼어서 길이가 2 미만이 되면 떼지 않는다.**

**왜 그렇게 정했나.** 한국어는 한 음절이 바뀌면 뜻이 완전히 달라지는 경우가 흔해서 **편집거리가 표기 변형의 근거가 되지 못한다.** 그리고 골드셋 정답 네 개(`G4` 로그인/로그 인 · `G5` 결제 수단/결제수단 · `G12` 회원 가입/회원가입 · `G13` e-mail/email/E-Mail)가 **모두 정규화만으로 잡히므로 편집거리가 애초에 필요하지 않았다.** 오타(`로그인`/`로그읜`)는 놓치게 되지만 그것은 표기 변형이 아니라 오타이고, 잡으려 들면 오탐이 늘어난다 — 이 프로젝트는 정밀도 우선이므로 놓치는 쪽을 택한다.

**영향.** 수용 기준 3번이 `G4` `G5` `G12` `G13`을 찾고 **`N9`를 묶지 않을 것**으로 강화됐다. §4의 규칙 표도 함께 갱신했다.

> **이 항목은 발표에 쓸 수 있다.** 함정을 심은 골드셋이 **초기 규칙의 오탐을 실제로 잡아내 규칙을 좁힌 사례**다. "품질을 어떻게 관리했나"라는 질문에 추상적인 답 대신 이 한 건을 들면 된다 — 채점표를 코드보다 먼저 만들어서 얻은 결과이기 때문이다.

### D-5 · 오프셋 계산에서 마크다운 문법을 어떻게 처리했는가 — 2026-09-08

**무엇이 문제였나.** `content`에 마크다운(`**`, `#`, 표)이 섞여 있을 때, 오프셋을 마크다운 제거 후 평문 기준으로 계산할지 원문 그대로 계산할지 정해야 했다.

**무엇을 바꿨나.** **원문(마크다운 포함) 그대로**를 기준으로 오프셋을 계산하기로 했다. 마크다운을 제거·정규화하는 전처리 단계를 두지 않는다. (`app/pipeline/normalize.py`의 `find_occurrences`/`make_snippet`이 이 원칙으로 구현됨)

**왜 그렇게 정했나.** Spring이 화면에 하이라이트할 때도 요청에 담아 보낸 `content`와 **같은 문자열**을 기준으로 렌더링한다. 서버가 임의로 마크다운을 벗겨내고 그 결과 기준으로 오프셋을 계산하면, Spring 쪽 원문과 인덱스가 어긋난다. 실제 fixtures 문서를 확인해 보면 `**로그인**`처럼 강조 기호가 용어를 **감싸기만** 하고 내부를 가르지 않으므로, 원문에 리터럴 문자열 검색을 해도 정상적으로 정확한 위치를 찾는다.

**영향.** 2단계(문서 파싱) `verify-offsets`가 5개 occurrence 전부(실제 fixtures 5장 기준)를 글자 단위로 통과했다. 표(table) 구문처럼 더 복잡한 마크다운 안에 표기가 걸리는 경우가 나오면, 그때 이 결정을 다시 검토한다.

### D-8 · VARIANT가 마크다운 강조 표시에 의존한다 — 알려진 리스크 — 2026-09-09

**무엇을 발견했나.** `pipeline/variant.py`의 후보 표기 발견 로직(`_extract_candidate_forms`)은 문서의 `**볼드**`/`` `코드` `` 강조 스팬**만** 후보로 본다. fixtures 문서가 핵심 용어를 거의 다 강조해 둬서 지금은 잘 작동하지만, **실제 프로덕션에서 팀이 올리는 문서가 강조 없이 평문으로만 쓰여 있으면 VARIANT는 후보를 아예 못 찾고 빈 결과를 낸다.** 우연한 버그가 아니라 지금 설계상 구조적인 한계다.

**SYNONYM/HOMOGRAPH(LLM, 4~5단계)는 이 문제가 없다.** `pipeline/llm.py`가 문서 원문 전체를 그대로 프롬프트에 넣어(§5 ③) Gemini가 강조 여부와 무관하게 전체 텍스트를 읽고 판단하기 때문이다. 규칙 기반(VARIANT)이 LLM 기반보다 오히려 문서 스타일에 더 취약하다는 뜻이다.

**어쩌다 발견했나.** "주문"(D-7) 탐지를 돕기 위해 "고빈도·다부서 표기를 뽑아 프롬프트에 힌트로 주는" 방법을 설계하다가, VARIANT와 같은 볼드/코드 추출기를 재사용하려 했더니 같은 약점을 그대로 물려받는다는 게 드러났다. 그래서 그 힌트 기능은 공백 기반(마크다운 무관)으로 다시 설계했다(D-9 참고 예정).

**지금 하지 않는 것.** VARIANT 자체를 지금 고치지 않는다 — fixtures 문서 기준으로는 통과하고 있고(§8-3), 실제 문서로 테스트할 근거가 아직 없다. 실제 문서에서 재현율이 낮게 나오면 그때 "공백 기반 후보 발견"으로 보강한다.

**영향.** 실제 팀 문서로 전환할 때(§11 이후) VARIANT 재현율을 반드시 재확인해야 한다 — fixtures에서 통과했다고 실제 문서에서도 통과한다는 보장이 없다.

### D-11 · 모델을 `gemini-3.5-flash-lite`로 교체 — 2026-09-09

**무엇이 문제였나.** D-10에서 `gemini-3.1-flash-lite`가 5회 연속 "주문"(단계별 포함 범위 차이형 동형이의)을 놓치는 안정적인 패턴을 확인했다. 프롬프트를 더 파고들기보다 다른 모델이 이 판단을 다르게 할지 확인해보기로 함.

**무엇을 바꿨나.** 사용자가 콘솔에서 확인 후 `.env`의 `GEMINI_MODEL`을 `gemini-3.1-flash-lite` → **`gemini-3.5-flash-lite`**로 교체. `app/pipeline/usage_log.py`의 `FREE_TIER_LIMITS`에 반영(RPM 30 · TPM 250,000 · RPD 1,500 — 이전 모델과 TPM이 다르다, 웹 검색 기준이라 콘솔에서 재확인 권장).

**모델 교체 중 발견한 버그.** `pipeline/llm.py`의 캐시 키(`_cache_path`)가 **프롬프트만** 해싱하고 **모델명은 해싱하지 않고 있었다.** 그래서 모델만 바꾸고 프롬프트가 그대로면, 이전 모델(`gemini-3.1-flash-lite`)의 캐시된 응답을 새 모델 호출인 것처럼 그대로 재사용할 뻔했다 — §6이 "sha256(프롬프트 + 입력)"이라고 명시했는데 모델이 빠져 있었다. `_cache_path(cache_dir, prompt, model)`로 고쳐서 모델도 해시에 포함시켰다. 이 버그가 있는 채로 모델을 바꿔 재시도했으면 "새 모델로 다시 확인했다"고 착각한 채 실제로는 옛 모델 결과를 그대로 보고할 뻔한 사례라 기록해 둔다.

**영향.** 이 교체 이후의 새 호출은 새 `promptHash`(모델명이 섞여 들어가므로)로 캐시된다 — 기존 `gemini-3.1-flash-lite` 캐시·이력과 자연스럽게 구분된다.

**실제 교체 결과 (6차 시도) — `gemini-3.5-flash-lite`는 더 나쁘다.** "주문"은 여전히 못 찾았고, 그 외에 **새로운 문제가 둘 생겼다**:
1. **처음으로 진짜 오탐이 나왔다**: `["결제 취소", "환불"]`을 SYNONYM으로 묶었다 — 이건 골드셋 `N1` 함정 그 자체다("조건이 다름"). `reason` 텍스트도 자체 모순적이다: *"승인 전 철회와 승인 후 반환을 구분하고 있으나... 의미가 혼용되어 사용되므로 구분하되... 결제 취소의 정의를 따른다"* — 스스로 다르다고 말해놓고 결국 묶었다. 정밀도 1.00 → **0.86**으로 하락(그래도 합격선 0.70은 넘음).
2. **기존에 5번 다 정확히 잡던 `정산`·`활성`까지 이번엔 하나도 안 잡혔다**(`consideredHomographCandidates`엔 둘 다 있었는데 최종에서 전부 빠짐). `gemini-3.1-flash-lite`보다 HOMOGRAPH 최종 판정에서 훨씬 더 보수적으로 구는 것으로 보인다.

**결론(6차 시도 시점).** 이번 교체는 "주문" 문제를 풀지 못했고, 오히려 다른 영역(정밀도, 기존에 되던 HOMOGRAPH)에서 퇴보했다. 사용자가 "조금 더 시도해보자"고 결정 — 아래 D-12에서 이어진다.

### D-17 · `DictionaryContrast` 계약 확정 — 2026-09-10

**무엇이 문제였나.** §11에 "계약이 정해지면 이 리포에 추가한다"고만 적혀 있고 실제 계약이 없었다. 사용자가 "사전집 대조" 테스트를 진행하려는데, 코드는커녕 요청/응답 모양조차 정의돼 있지 않았다 — AGENTS.md 원칙("계약을 임의로 바꾸지 마라", "모르는 게 있으면 여기 적고 물어라")에 따라 코드보다 계약을 먼저 확정했다.

**무엇을 정했나.**
1. **범위를 좁혔다.** "변경 사항을 찾는다"를 신규 용어 발굴이 아니라 **"이미 사전집에 등재된 용어가 문서에서 선호 표기가 아닌 다른 등재 표기(synonym)로 쓰였는지 찾아 치환을 제안한다"**로 정의(사용자 확인). 신규 용어 발굴은 이미 `extract`의 몫이라 중복하지 않는다.
2. **스키마를 재사용했다.** 사전집 한 항목은 `ExistingTerm`(§3.1)과 완전히 같은 모양이고, 신규 문서는 `DocumentInput`(§3.1)과 완전히 같은 모양이다 — 새 타입을 만들지 않고 그대로 재사용(§12.1).
3. **오프셋 엔진을 재사용했다.** `normalize.py`의 `find_occurrences`/`make_snippet`을 그대로 호출한다 — 오프셋 계산 로직을 두 번 만들지 않는다.
4. **1차는 규칙 기반으로만 간다.** VARIANT 단계와 같은 이유 — 문맥 판단(LLM)이 필요하다는 게 골드셋 재현율 부족으로 확인되기 전까지는 추가하지 않는다(AGENTS.md "형태소 분석기·임베딩 클러스터링을 넣지 마라" 원칙과 같은 결).
5. **같은 리포, 별도 모듈·엔드포인트로 진행.** `extract` 파이프라인 코드(`variant.py`/`synonym.py`/`llm.py`)는 건드리지 않고 `app/pipeline/contrast.py`를 새로 만든다. 픽스처도 `fixtures/contrast/`로 완전히 분리해 기존 `gold.csv`/`docs/*.md`를 건드리지 않는다.

**영향.** §11의 DictionaryContrast 줄을 "계약 확정"으로 갱신, §12를 새로 추가. `extract` 쪽 코드·픽스처·채점 결과에는 영향 없음(완전히 분리된 모듈이라 회귀 위험 없음).

- 정밀도(구조적 오탐 기준) 1.00, 재현율 1.00
- `charStart`/`charEnd` 8건 전부 원문과 바이트 단위로 재검증(직접 슬라이싱 대조) — 전부 일치

**알려진 리스크(§10 D-8과 같은 성격).** 동의어 문자열이 짧고 다의적일수록(예: "등급") 리터럴 매칭이 문맥과 무관하게 걸린다. 지금은 트랩으로 남겨두고 "본질적 한계"로 문서화한다 — VARIANT의 마크다운 의존성(D-8)과 마찬가지로, 실제 사전집 데이터에서 이 문제가 얼마나 자주 나오는지 확인되기 전에는 LLM 문맥 판단을 추가하지 않는다(AGENTS.md 원칙).

**결론.** §12.4 C-1·C-2 통과. `extract` 파이프라인 코드·픽스처·채점 결과에는 영향 없음(완전히 분리된 모듈).

### D-19 · `DictionaryContrast`를 2단계(규칙 + LLM 정의 기반)로 확장, 골드셋 25개로 확대 — 2026-09-10

**무엇이 문제였나.** D-17에서 §12를 "규칙 기반만"으로 좁혔는데, 사용자가 애초에 LLM을 넣으려 했던 이유를 명확히 밝혔다: "사전집에서 유비쿼터스 언어, 그 언어에 대한 정의 부분을 활용하여, 문서에서 맥락상으로 찾아야하는 단어들을 찾기 위함". 즉 **등재되지 않은 표현이라도 정의가 가리키는 개념을 문서가 맥락상 말하고 있으면 찾아야 하는데**, 그 시점의 `ExistingTerm`엔 `definition` 필드 자체가 없어 구조적으로 불가능했다. `extract`처럼 규칙(리터럴) 먼저 테스트하고 LLM(정의 기반)을 이어붙이는 방향, 골드셋을 `extract`와 같은 규모(25개)로 확대하는 방향, 사전집을 새로 지어내지 말고 용어 추출 때 다룬 도메인을 재사용하는 방향으로 확정했다.

**무엇을 바꿨나.**
1. **`DictionaryEntry(ExistingTerm)`를 추가**해 `definition: str`을 얹었다. `ExistingTerm`(§3.1, `extract`와 공유하는 타입) 자체는 건드리지 않았다 — 상속으로만 확장
2. **`ContrastSuggestion`에 `method: "rule"|"llm"`을 추가** — 어느 단계가 찾았는지 구분해야 채점·리포트가 의미 있다
3. **LLM 단계(`app/pipeline/contrast_llm.py`)를 신규 모듈로 추가** — `pipeline/llm.py`(extract의 SYNONYM/HOMOGRAPH 호출)와 완전히 같은 인프라(캐시·카운터·재시도·`usage_log`)를 그대로 재사용했다. 새 프롬프트 4개(`prompts/contrast_01_role.md`~`contrast_04_input.md`)만 추가
4. **환각 방지 방어 검증 2가지**를 코드에 넣었다 — LLM이 돌려준 `termId`가 사전집에 실재하는지, `matchedText`가 문서에 실제로 존재하는지. 둘 다 실패하면 그 매치는 버리고 경고를 찍는다(조용히 넘기지 않는다)
5. **사전집을 용어 추출 도메인에서 재사용**했다 — `fixtures/workspace.json`의 `existingTerms`(t-001·t-002) + `fixtures/gold.csv`의 SYNONYM/VARIANT 그룹 11개(G1·G2·G3·G4·G5·G8·G9·G10·G11·G12·G13) = 13항목. 각 `definition`은 `gold.csv`의 `note` 컬럼에서 가져왔다. **HOMOGRAPH 4개(G6 주문·G7 활성·G14 정산·G15 등급)는 의도적으로 제외했다** — "치환할 선호 표기가 없다"는 게 이유다: 이것들은 표기를 하나로 통일하는 문제가 아니라 부서마다 다른 뜻을 하나로 고정하는, §12와는 다른 성격의 문제다
6. **문서를 새로 만들지 않고 재사용**했다 — `fixtures/docs/*.md` 5장을 `../docs/...` 상대경로로 그대로 참조(중복 없음). LLM 단계 전용으로 신규 문서 1장(`9월_CS_이슈_노트.md`)만 추가 — 등재된 동의어 문자열을 전혀 안 쓰고 개념만 풀어써서 리터럴 매칭은 반드시 놓치게 만들었다
7. **골드셋을 25행(정답 15·함정 10)으로 확대** — 정답 13개는 규칙 단계용(리터럴 위치를 직접 읽어서 확인), 2개는 LLM 단계 전용(신규 문서의 패러프레이즈, `termId`+`documentId`만 일치하면 인정 — LLM 산출 문구를 정확히 예측할 수 없어서). 함정 10개는 `extract`의 기존 N1·N2·N6·N7·N8·N10과 같은 소재를 재사용했는데, 이번엔 목적이 다르다 — "사전집에 없는 근접 개념에 LLM이 등재된 termId를 억지로 갖다 붙이는 환각을 하지 않는가"를 검증하는 것이 핵심이다. 특히 HOMOGRAPH로 제외한 "등급"·"주문"에 대한 트랩(N-7·N-8)이 데모 핵심 용어라 더 예민하게 다뤘다

**결과 (2026-09-10 실측, `gemini-3.5-flash`, API 1회 호출).**

- LLM 단계: 일치 2/2, 오탐 0, 정밀도·재현율 1.00 — 두 패러프레이즈(t-101 "구독 일시정지", t-103 "리워드 포인트") 모두 등재된 동의어 없이 정확히 찾아냈고, `reason`도 타당했다

### D-20 · contrast 결과 이력·LLM 사용량 로그를 extract와 완전히 분리 — 2026-09-10

**무엇이 문제였나.** `contrast` 명령이 `extract`와 달리 결과를 자동으로 이력에 남기지 않았다. 그리고 `contrast_llm.py`(§12 2단계)가 `extract`의 공유 로그(`logs/llm_usage.jsonl`·`logs/llm_call_details.jsonl`)에 그대로 적고 있었는데, 그 로그의 스키마(`synonymGroupsFound`/`homographsFound`/`outputSynonymGroups`/`outputHomographs`)는 extract 전용으로 설계된 것이라 contrast가 적으면 그 필드들이 항상 0/빈 배열로 찍혔다(실제로 D-19 검증 때 `LlmCallDetail`에 `outputContrastMatches`를 임시로 얹어 이 문제를 눈가림했다). 토큰을 세는 방식 자체는 같지만, "이 호출에서 뭘 찾았는지"를 나타내는 기준이 기능마다 다르다는 게 근본 원인이었다.

**무엇을 바꿨나.**
1. **`out/contrast_history/` 신설** — `_archive_to_history()`에 `dest_dir` 파라미터를 추가해 `extract`(`out/history/`)와 `contrast`(`out/contrast_history/`)가 완전히 다른 폴더에 쌓이게 했다. `contrast` 명령도 `extract`처럼 매 실행마다 자동으로 스냅샷을 남기고, 라벨을 붙이고 싶을 때 쓰는 `archive-contrast` 명령도 대칭으로 추가했다
2. **`app/pipeline/contrast_usage_log.py` 신설** — `logs/contrast_llm_usage.jsonl`/`logs/contrast_llm_call_details.jsonl`에 독립적으로 쌓는다. 필드도 contrast에 맞게 새로 정의했다: `matchesReturned`(LLM이 원래 돌려준 수)/`matchesAccepted`(검증 통과해 채택된 수)/`matchesDropped`(환각으로 버려진 수), 상세 로그엔 `droppedMatches`(버려진 이유까지)를 남긴다 — extract 로그엔 없는 항목들이다
3. **무료 티어 한도 표(`FREE_TIER_LIMITS`)는 중복 정의하지 않고 `usage_log`에서 그대로 가져다 쓴다** — 모델별 RPD는 Google 쪽 사실이라 기능마다 따로 관리할 이유가 없다
4. **`usage_log.LlmCallDetail`에 임시로 얹었던 `outputContrastMatches` 필드는 제거했다** — 이제 진짜 분리된 파일이 생겼으니 필요 없다(이 필드를 쓴 실제 로그 기록이 없어 하위 호환 문제 없음)
5. **공유 RPD 쿼터를 놓치지 않도록 처리** — `extract`와 `contrast`의 LLM 호출은 로그 파일은 분리돼 있어도 **같은 Gemini 모델을 쓰면 같은 일일 쿼터(RPD)를 나눠 쓴다.** 그래서 `usage-report`와 새로 만든 `contrast-usage-report` 둘 다 "오늘 이 모델 실제 API 호출"을 계산할 때 **두 로그를 전부 읽어 합산**하고(`_today_real_calls_combined()`), 출처별로 몇 회인지 병기한다. 한쪽 로그만 보면 실제 소모량보다 적게 보이기 때문이다

**검증.** `contrast --skip-llm`을 두 번 연속 실행해 `out/contrast_history/`에 스냅샷 2개가 쌓이고 `out/history/`(extract)는 그대로인 것을 확인. `contrast`(LLM 포함)를 한 번 더 실행해 `logs/contrast_llm_usage.jsonl`/`logs/contrast_llm_call_details.jsonl`이 새로 생기고 `logs/llm_usage.jsonl`(extract)의 줄 수는 그대로(27줄)인 것을 확인. `usage-report --today`/`contrast-usage-report --today` 둘 다 정상 동작하고 "오늘 이 모델 실제 호출" 숫자가 두 출처를 정확히 합산해 보여주는 것을 확인.

**참고.** 이 작업 전에 `logs/llm_usage.jsonl`에 이미 남아있던 `stage="contrast"` 옛 로그 줄(D-19 검증 당시 기록)은 **소급해서 옮기거나 고치지 않았다** — 그 시점엔 실제로 그 파일에 적었던 게 사실이므로, 과거 기록을 손대지 않는다(AGENTS.md "숫자·기록을 꾸미지 마라" 원칙). 새 호출부터만 분리된 로그에 쌓인다.

**참고 2 (이 작업과 무관하게 관찰됨).** 검증 중 `.env`의 `GEMINI_MODEL`이 이전 세션에서 확정했던 `gemini-3.5-flash`가 아니라 `gemini-3.1-flash-lite`로 바뀌어 있는 것을 발견했다 — 이 세션에서 건드리지 않았다. 참고로 이 모델로 LLM 단계를 돌리니 `G-15`(리워드 포인트 패러프레이즈)를 놓쳐 재현율이 0.93으로 낮아졌다(D-19의 `gemini-3.5-flash` 결과는 1.00). `.env`를 되돌릴지는 사용자 판단이 필요해 임의로 바꾸지 않았다.

### D-21 · contrast 픽스처를 문서 6개에서 단일 문서(자체 완결형)로 통합 — 2026-09-10

**무엇이 문제였나.** D-19에서 신규 문서(`9월_CS_이슈_노트.md`)는 LLM 전용 정답 2개(`G-14`·`G-15`)만 위한 짧은 문서였고, 나머지 23개(정답 13·함정 10)는 `extract`의 실제 문서 5장(`../docs/*.md`)에 흩어져 있었다. 사용자가 이 신규 문서가 "너무 작다"고 지적 — 골드셋 25개를 전부 이 문서 하나로 테스트할 수 있게 다시 써달라는 요청이었다.

2. `fixtures/contrast/dictionary.json`의 `documents`에서 `d-001`~`d-005`(`../docs/*.md` 상대경로 참조)를 **제거**했다 — 이제 `d-201` 하나로 골드셋 25개 전부가 검증되므로 더 필요 없다. 사전집 13항목 자체(재사용 출처는 그대로 `extract`의 `gold.csv`/`workspace.json`)는 안 바꿨다 — 이번 변경은 "문서" 재사용만 그만둔 것이고 "사전집 도메인" 재사용(D-19)은 유지한다

**결과 (2026-09-10, `gemini-3.1-flash-lite`, API 1회 호출, inputTokens 4426/outputTokens 400).**

- LLM 단계가 채점 대상(`G-14`·`G-15`) 외에 2건을 추가로 더 찾았다(`t-102` 구독 해지, `t-111` 동시 접속 제한) — 골드셋엔 없지만 함정도 아니라 오탐으로 잡히지 않았다. 문서에서 리터럴 매칭된 문장 바로 옆에 정의를 풀어 설명하는 문장을 같이 쓴 게 원인으로 보인다(예: "탈퇴는 되돌릴 수 없고 30일 뒤 개인정보가 삭제된다"가 `definition`과 거의 같은 표현). 틀린 결과는 아니지만, 문서를 쓸 때 정의 문장을 그대로 반복하면 LLM이 "너무 쉽게" 맞힐 수 있다는 걸 기록해둔다 — 실제 서비스 문서는 이렇게 정의를 그대로 되풀이하지 않을 가능성이 높다
- 이전(D-19, `gemini-3.5-flash`, 문서 6개) 결과와 정밀도·재현율 숫자는 동일(1.00/1.00)하지만, **API 호출당 입력 토큰이 8019 → 4426으로 줄었다** — 문서 6개 대신 1개만 프롬프트에 들어가서다. 문서를 줄이는 게 토큰 비용에도 유리하다는 부수적 확인

**결론.** §12.4 C-1·C-2·C-3 재검증 통과. 이제 `fixtures/contrast/`는 다른 픽스처 세트(`fixtures/docs/*.md`)에 대한 상대경로 의존이 전혀 없는 완전한 자체 완결형 픽스처다.

### D-22 · 규칙 단계를 완전히 제거, LLM 단독(정의 기반)으로 전환 — 2026-09-10

**무엇이 문제였나.** 실제 프로젝트의 DB는 사전집 항목에 `synonyms`(동의어 목록)를 저장하지 않기로 확정됐다 — 저장되는 건 **표준어(선호 표기)와 정의뿐**이다. D-19에서 만든 "규칙 단계"(`find_contrast_suggestions`)는 전적으로 `synonyms`를 리터럴로 스캔하는 로직이라, 실제 서비스에서는 입력 자체가 항상 빈 배열이라 **영원히 아무것도 못 찾는다.** 정밀도·재현율 문제가 아니라, 이 단계가 의존하는 데이터가 실제로는 존재하지 않는다는 더 근본적인 계약 불일치였다.

**무엇을 바꿨나.**
1. `contrast.py`에서 `find_contrast_suggestions()`(규칙 매칭)와 그 전용 헬퍼(`_euro_or_ro`)를 **삭제**했다. `app/cli.py`의 `contrast` 명령도 이제 `find_llm_contrast_matches()`만 호출한다
2. `--skip-llm` 플래그를 제거했다 — LLM이 유일한 메커니즘이라 이 옵션을 쓰면 결과가 항상 빈 배열이라 의미가 없다
3. **스키마는 그대로 뒀다**(사용자 결정) — `DictionaryEntry`는 여전히 `ExistingTerm`을 상속하고 `synonyms` 필드도 남아있지만, 실제로는 항상 빈 배열로 들어온다고 취급한다. 계약을 다시 바꾸는 것보다 하위 호환을 유지하는 쪽을 택했다
4. `contrast_llm.py`의 프롬프트 빌드에서 사전집 JSON을 보낼 때 `synonyms`를 **제외**했다(늘 빈 배열인 필드는 노이즈다) — `termId`/`preferredForm`/`englishName`/`definition`만 보낸다
5. 방어 검증을 하나 추가했다 — LLM이 돌려준 `matchedText`가 `preferredForm`과 정확히 같으면 버린다. 예전 규칙 단계의 `if form == preferredForm: continue`가 하던 일 중, 코드로 결정론적으로 보장할 수 있는 부분만 되살린 것이다
6. 프롬프트(`contrast_01_role.md`·`contrast_02_forbidden.md`)를 다시 썼다 — "규칙 단계가 리터럴은 이미 다 찾았으니 그 반대만 찾아라"는 전제를 지우고, **리터럴 그대로 쓰인 경우와 정의만 풀어쓴 경우를 전부 한 번에 찾으라**고 명시했다
7. 채점(`compute_contrast_score`)을 규칙/LLM/합산 3단에서 **1단으로 단순화**했다 — 모든 매칭이 LLM이므로 단계 구분 자체가 의미 없어졌다. `gold.csv`에서 `expected_method` 컬럼을 제거했다(`termId`+`documentId`만으로 판정, `expected_text`는 참고용으로만 남김)
8. `fixtures/contrast/dictionary.json`의 13항목 전부 `synonyms: []`로 바꿔 실제 DB 모양을 반영했다

**결과 — 모델에 따라 재현율이 크게 갈렸다(실측 그대로 기록).**
- `gemini-3.1-flash-lite`로 첫 실행: 일치 **7/15**, 오탐 0, 정밀도 1.00, **재현율 0.47.** `droppedMatches`는 0건(환각 없음)이지만 애초에 리터럴로 확실한 것(이용자·pg_error·탈퇴·마일리지·로그 인·결제수단·회원가입)까지 절반 가까이 놓쳤다 — 예전엔 규칙 단계가 결정론적으로 보장해주던 것들이라, 그 안전망이 없어지자 약한 모델의 한계가 그대로 드러났다
- 같은 프롬프트·같은 문서로 `--model gemini-3.5-flash`만 바꿔 재실행: 일치 **15/15**, 오탐 0, 정밀도·재현율 **1.00.** `matchesReturned=matchesAccepted=23`, 버려진 매치 0건
- `charStart`/`charEnd` 23건 전부 두 문서(`9월_CS_이슈_노트.md`·Gemini가 생성한 `주간 운영 이슈 및 지표 점검 리포트.md`) 원문과 바이트 단위 일치 확인

**결론.** LLM 단독 설계 자체의 결함이 아니라 **모델 성능 의존도가 커졌다는 게 확인된 것**이다 — 규칙 단계가 있을 때는 리터럴 매칭을 결정론적 코드가 보장해줬지만, 이제는 그 부분까지 LLM이 놓치지 않아야 한다. `.env`는 계속 `gemini-3.1-flash-lite`로 남아있다(사용자가 이 세션 밖에서 바꾼 값, 이 세션에서 되돌리지 않음) — **이 모델로 §12를 운영하면 재현율이 낮을 수 있다는 걸 기록해둔다.** 실제 배포 전에는 `gemini-3.5-flash`처럼 이미 검증된 모델로 `.env`를 맞추는 걸 권장.

**결론.** extract(D-15·D-16)와 같은 결론을 §12에도 그대로 적용한다 — RPD 쿼터를 아끼기 위해 추가 재시도는 멈춘다. `gemini-3.8-flash`도 같은 계열이라 시도 전에 사용자와 진행 여부를 먼저 확인한다.

### D-29 · §12 재현율 개선안(사고 유도 스키마)의 확장성 제약 — 알려진 리스크, 지금은 안 만듦 — 2026-09-11

**무엇이 문제인가.** §12 재현율을 올리는 방법으로 "사고 유도 스키마"(`consideredTermIds` — 사전집 termId 전부를 판정 전에 나열하게 스키마로 강제, HOMOGRAPH의 `consideredHomographCandidates`·D-9와 같은 기법)를 검토했는데, 이건 **사전집 크기에 비례해 비용·품질 리스크가 커지는 구조**다:
- 입력 토큰: 사전집 전체(termId·preferredForm·definition)를 프롬프트에 넣는 건 이 방법과 무관하게 이미 있던 비용이고, 사전집이 커지면 그 자체로 선형 증가한다
- 출력 토큰: `consideredTermIds`가 사전집 크기만큼 추가로 늘어난다(항목당 몇 토큰 수준)
- **더 걱정되는 건 토큰 비용이 아니라 품질 저하** — 사전집이 수백 개가 되면 모델이 전부 성실하게 검토하는 대신 대충 훑고 넘어갈 위험이 있다(주의력 분산). 지금 13개에서도 일부를 놓치는데, 그 배수로 늘면 오히려 재현율이 더 나빠질 수 있다

**지금은 만들지 않는다.** 사전집이 13개뿐인 지금은 이 리스크가 이론적일 뿐이고, AGENTS.md의 "필요성이 증명되기 전엔 복잡도를 늘리지 마라" 원칙(§11의 "임베딩 클러스터링 — 후보가 수백 개가 된 뒤에"와 같은 결)을 그대로 적용한다.

**분기점 — 아래 중 하나라도 실제로 확인되면 그때 재검토한다:**
1. 사전집 항목 수가 **수십 개(대략 50개)를 넘어서는 시점** — 규모 자체가 근거
2. 그 규모에서 **실측으로 재현율 하락이나 입력 토큰 급증이 확인되는 시점** — 추측이 아니라 `score-contrast`/`contrast-usage-report` 숫자로 근거를 남긴다

**그때 할 일 (지금 미리 만들지 않고, 분기점에 도달하면 설계).** HOMOGRAPH(§10 D-9)가 이미 쓴 것과 같은 2단계 방식을 그대로 재사용한다 — 새로 발명하지 않는다:
1. 저렴한 방법(형태소 분석기·임베딩 없이 순수 텍스트 통계, `variant.py`의 `find_frequent_terms`와 같은 방식)으로 "이 문서와 관련 있을 법한 사전집 항목"을 미리 20~30개로 좁힌다
2. 사고 유도 스키마(`consideredTermIds`)는 사전집 전체가 아니라 **좁힌 후보에만** 적용한다

### D-38 · Gemini API 키 순차 폴백 — 2026-09-11

**무엇이 문제였나.** D-15/16/28/36에서 반복 확인된 문제 — 모델 하나당 무료 티어 RPD가 (특히 `gemini-3.5-flash` 계열은 20으로) 하루 테스트 도중 소진되면, 키가 1개(`GEMINI_API_KEY`)뿐이라 그 모델은 그날 아예 못 썼다.

**무엇을 했나.** 새 공유 모듈 `app/pipeline/api_keys.py`를 만들어 `llm.py`·`contrast_llm.py` 양쪽이 재사용하게 했다(D-20이 `usage_log`를 공유한 것과 같은 원칙).
- `GEMINI_API_KEY_1`, `_2`, ... 를 순서대로 읽는다. 번호 붙은 키가 하나도 없으면 기존 `GEMINI_API_KEY`(단수) 하나로 그대로 동작한다(마이그레이션 강제 없음).
- 1번 키부터 시도하다가, `google.genai.errors.ClientError`의 `.code`가 `401`(인증 실패)·`403`(권한 없음)·`429`(쿼터 소진 `RESOURCE_EXHAUSTED`) 중 하나면 "이 키 자체의 문제"로 보고 다음 키로 넘어간다. 그 외 4xx(예: 400 — 프롬프트/스키마 문제)는 폴백하지 않고 그대로 raise한다 — 키를 바꿔도 똑같이 실패할 문제를 "키 탓"으로 착각하면 진짜 버그를 놓친다.
- **실제로 무효한 키로 검증하다가 계획과 다른 사실을 발견했다**: 무효 키는 401/403이 아니라 **`400 INVALID_ARGUMENT`**로 온다(`message: "API key not valid"`). code만 보면 "진짜 프롬프트/스키마 문제로 인한 400"과 구분이 안 돼, `.code` 체크만으로는 이 케이스를 놓쳤을 것이다. 대신 응답 JSON 안쪽(`.details["error"]["details"]`)에 `reason: "API_KEY_INVALID"`가 실려 오길래, 이 reason을 추가로 검사해서(코드 기반 판정은 그대로 두고) 이 케이스만 더 잡도록 고쳤다 — `is_key_specific_failure()`가 `code in (401,403,429)` 또는 `reason in {API_KEY_INVALID, PERMISSION_DENIED, UNAUTHENTICATED}`일 때 폴백한다.
- §6의 "4xx는 재시도하지 않는다" 규칙은 그대로 유지된다 — 이건 "같은 키로 재시도"가 아니라 "다른 키로 폴백"이라는 별개의 동작이다. 키 하나당 5xx 재시도(최대 2회, 지수 백오프)도 그대로다.
- 로그(`LlmCallLog`/`ContrastCallLog`)엔 실제 키 값이 아니라 **몇 번째 키로 성공했는지(`keyIndex`)만** 남긴다(AGENTS.md: "로그·커밋·에러 메시지에 절대 넣지 마라").

**결과.** 실제 RPD를 소진시키지 않고 검증하기 위해, `.env`를 임시로 `GEMINI_API_KEY_1=`(일부러 틀린 값)·`GEMINI_API_KEY_2=`(실제 유효 키)로 바꾸고 `extract --model gemini-3.1-flash-lite --no-cache`를 1회 호출 — key1이 `400 INVALID_ARGUMENT`(`API_KEY_INVALID`)로 막히고 key2로 자동 폴백해 정상 결과(`candidates=9개`)가 나오는 것을 확인했다. `logs/llm_usage.jsonl` 마지막 줄의 `keyIndex`가 `2`로 찍혔다. 검증 후 `.env`는 원래 상태(키 1개)로 되돌렸고, 그 상태로 다시 호출해 `keyIndex=1`로 기존과 동일하게 동작함(회귀 없음)을 확인했다. `contrast`도 같은 헬퍼를 쓰므로 캐시 히트로 1회 더 확인 — 정상.

**확장성 기록 — 다음 분기점이 되면 재검토한다.** 지금은 순차 폴백만 구현했다. 라운드로빈(사전 분산)은 기각했다 — 각 CLI 호출(`extract`/`contrast`)이 독립된 프로세스라, 회전 상태("다음엔 몇 번 키 차례")를 어딘가에 영속시켜야 라운드로빈이 의미가 있는데, 지금 규모(키 2~3개, 테스트성 호출 몇십 회/일)에서 그 복잡도를 정당화할 이득이 없다. 다음 조건이 둘 다 충족되면 재검토한다: (1) 6단계(FastAPI 래핑)가 완료돼 상시 프로세스가 생기고, (2) 실측으로 특정 키에 트래픽이 쏠려 다른 키가 노는 게 실제 문제로 확인될 때. 그전까지는 순차 폴백으로 충분하다.
참고로, 키 개수가 늘어나면 최악의 경우(모든 키가 5xx로 실패) 프로세스당 실제 호출 수가 `키 개수 × 3`까지 늘 수 있어 — `MAX_LLM_CALLS=20`(§6 호출 카운터)과의 여유를 키를 늘릴 때마다 같이 확인해야 한다.
**키별 RPD 잔량 추적은 이번에 넣지 않았다** — 지금 RPD 계산(`cli.py`의 `_today_real_calls_combined`)은 모델명 기준이라, 키 기준으로 바꾸려면 로그 스키마를 더 키워야 하는데 지금 측정된 필요("막히면 다음 키로 폴백") 이상으로 벌리지 않는다.

### D-39 · Gemini 모델 폴백 — `--model`에 콤마로 체인 지정 — 2026-09-11

**무엇이 문제였나.** D-38로 키 폴백은 됐지만, `gemini-3.5-flash`(정밀도·재현율 최고, D-37/D-33)를 등록된 키 전부로 시도해도 소진되면 그 이상은 방법이 없었다 — 지금까지 D-14~D-37에서 수동으로 해온 "이 모델 막히면 다른 모델로" 전환을 자동화해달라는 요청.

**무엇을 했나.** 새 공유 모듈 `app/pipeline/model_chain.py`(`api_keys.py`와 짝) — `parse_model_chain()`(콤마 split) + `is_model_unavailable_failure()`(`ServerError`는 항상 True, `ClientError`는 `api_keys.is_key_specific_failure()`에 위임). `llm.py`/`contrast_llm.py`에 모델 루프를 하나 더 둘렀다 — **`.env`에 새 변수는 만들지 않는다(사용자 결정)**, 대신 `--model`에 콤마로 나열한다: `--model "gemini-3.5-flash,gemini-3.6-flash,gemini-3.5-flash-lite,gemini-3.1-flash-lite"`. 콤마 없이 모델 하나만 주면(D-24~D-37에서 쓴 모든 방식) 길이 1짜리 체인이 되어 폴백 분기 자체가 실행되지 않는다 — 재현성 테스트 관행이 전혀 안 바뀐다. 모델이 바뀌면 그 모델의 키 폴백(D-38)은 1번 키부터 다시 시작한다. 로그엔 `modelIndex`(몇 번째로 폴백했는지)를 `keyIndex`와 나란히 남긴다.

**결과 — 계획과 다른 사실을 또 발견했다.** 존재하지 않는 모델명(`gemini-not-a-real-model`)으로 검증해보니 `404 NOT_FOUND`로 왔다 — 이건 401/403/429/`API_KEY_INVALID` 어디에도 안 걸려서 **폴백하지 않고 즉시 실패한다.** 계획 없이 처음부터 의도한 동작이었다: 모델 자체가 없다는 건 오타·설정 실수일 가능성이 커서, 조용히 다음 모델로 넘어가면 그 실수를 못 보고 지나칠 수 있다(§6 "4xx는 재시도하지 않는다"·D-38의 400-프롬프트-문제 판단과 같은 원칙). 실제 진짜 트리거 조건(모든 키가 인증/쿼터 문제로 막힘)은 임시로 등록된 키 전부를 무효화하고 `["gemini-3.1-flash-lite", "gemini-3.5-flash-lite"]` 체인으로 호출해 검증 — 두 모델 다 시도했다는 걸 `_call_count`(2)로 확인했다(둘 다 같은 무효 키라 결국 실패하지만, "다음 모델로 넘어갔는지"는 정확히 이걸로 확인된다). 콤마 없는 단일 모델 호출도 `modelIndex=1`로 기존과 동일하게 동작(회귀 없음). 검증 후 `.env`는 원상복구했다.
**참고**: 이 세션 도중 사용자가 실제로 `GEMINI_API_KEY_1`~`_4`(키 4개)를 `.env`에 등록해, D-38의 키 폴백이 이제 실사용 가능한 상태다.

**확장성 기록.** 라운드로빈은 D-38과 같은 이유로 기각 — 상시 프로세스 없이는 회전 상태를 영속시키는 복잡도가 이득을 못 넘는다. 재검토 분기점도 동일: (1) 6단계(FastAPI) 완료, (2) 실측으로 로드 쏠림이 확인될 때. 모델·키 조합이 늘어나면 최악의 경우(전부 5xx) 프로세스당 호출 수가 `모델 개수 × 키 개수 × 3`까지 늘 수 있어 `MAX_LLM_CALLS=20`과의 여유를 계속 확인해야 한다.

### D-40 · 모델 폴백을 `.env` 기본값으로 + 5xx도 키 전부 순회하도록 수정 — 2026-09-11

**무엇이 문제였나 (2가지).**
1. D-39는 매번 `--model`에 콤마로 체인을 타이핑해야 했다 — 사용자가 "기록이 되어야 `--model` 없이도 알아서 모델을 바꿀 수 있다"고 요청. 쉘 별칭/스크립트 대안도 제시했지만, 사용자는 **`.env`에 저장하는 방식**을 원했다(키(`GEMINI_API_KEY_1`)와 같은 패턴).
2. 이 논의 중 사용자가 D-38/D-39 설계의 허점을 짚었다: **지금 코드는 503(ServerError)이 나면 그 모델의 남은 키를 확인도 안 하고 곧장 다음 모델로 넘어간다.** 이건 "503은 서버 과부하라 키를 바꿔도 소용없다"는, 키가 1개뿐이던 D-15/16 시절 경험을 **검증 없이 일반화한 가정**이었다 — 키가 여러 개면 서로 다른 GCP 프로젝트/쿼터일 수 있어 이 가정이 틀릴 수 있다. 숫자를 꾸미지 않고 그대로 인정한다: 이건 실측으로 확인한 게 아니라 추측이었다.

**무엇을 했나.**
1. `model_chain.py`에 `load_default_model_chain()` 추가 — `GEMINI_MODEL_1`, `_2`, ... 를 순서대로 읽고, 번호 붙은 게 없으면 기존 `GEMINI_MODEL`(단수)로 폴백(`api_keys.load_api_keys()`와 동일 패턴, 마이그레이션 강제 없음). `llm.py`/`contrast_llm.py`의 모델 체인 결정을 `model_chain = parse_model_chain(model) if model else load_default_model_chain()`으로 바꿔, **`--model`을 명시하면 그게 `.env` 체인을 완전히 덮어쓰고(재현성 테스트 그대로 유지), 안 주면 `.env` 체인이 자동으로 쓰이도록** 했다. `cli.py`에서 `GEMINI_MODEL`을 직접 읽던 다른 3곳(`extract`의 `--skip-llm` 표시용, `usage-report`·`contrast-usage-report`의 한도 조회)도 이 함수의 1번째 값을 쓰도록 맞췄다.
2. 키 루프의 `except errors.ClientError` 한 갈래였던 걸 `except errors.ClientError`/`except errors.ServerError` 두 갈래로 나눠, **5xx도 429/401/403과 동일하게 "남은 키가 있으면 다음 키로" 넘어가도록** 고쳤다. 모델 루프로 올라가는 건 등록된 키를 전부 시도(5xx 포함)한 뒤뿐이다. `is_model_unavailable_failure`(model_chain.py)는 로직 변경 없음 — 이미 이 구조에 맞게 짜여 있었다.

**결과.** 사용자가 세션 도중 실제로 `.env`에 `GEMINI_MODEL_1=gemini-3.5-flash`·`_2=gemini-3.6-flash`·`_3=gemini-3.5-flash-lite`·`_4=gemini-3.1-flash-lite`를 미리 등록해둔 상태였다 — `load_default_model_chain()`이 이 4개를 정확히 순서대로 반환하는 것을 바로 확인. `--model` 없이 `extract`/`contrast`를 실행하니 자동으로 1번(`gemini-3.5-flash`)이 쓰였고(`modelIndex=1`), `--model gemini-3.1-flash-lite`(단일)로 명시하면 `.env`의 4개 체인을 무시하고 정확히 그 모델만 쓰는 것도 재확인(회귀 없음, `modelIndex=1`). `usage-report`/`contrast-usage-report`에도 `(폴백 체인 4개 중 1번째)` 표시를 추가해 1번째 모델 기준이라는 걸 명확히 했다.
**5xx-키-순회 부분은 실제 503을 강제로 재현할 방법이 없어(Google 서버 상태), 코드 경로 확인으로만 검증했다** — 다음에 실제로 503이 발생하면(D-15/16/28처럼 3.7/3.8-flash에서 재현될 가능성이 높다) 로그로 실측 재확인할 것.

**확장성 기록.** D-39와 동일 — 라운드로빈은 여전히 기각, 재검토 분기점도 동일(6단계 완료 + 로드 쏠림 실측). 이번에 5xx도 키를 전부 순회하게 되면서, 모델·키 조합이 많을 때 5xx 시나리오의 최악 호출 수(`모델 개수 × 키 개수 × 3`)가 실제로 발생할 가능성이 D-39 때보다 커졌다 — `MAX_LLM_CALLS` 여유를 키·모델을 늘릴 때마다 계속 확인해야 한다는 점을 다시 강조.

## 12. DictionaryContrast 계약 — 사전집 대조

> §11에서 "다음 단계"로 미뤄뒀던 것을 D-17(2026-09-10)에서 계약 확정. `extract`(§3)와는 별개의 엔드포인트·모듈이다 — **신규 용어를 찾는 게 아니라, 이미 사전집에 등재된 용어가 문서에서 어떻게 쓰였는지**를 찾는다.
>
> **LLM 단독(정의 기반)이다(D-22, 2026-09-10).** 한때는 "규칙 단계(등재된 동의어 문자열을 리터럴로 스캔) + LLM 단계(정의 기반 맥락 매칭)" 2단계였는데(D-19), **실제 서비스 DB가 사전집 항목에 동의어 목록(`synonyms`)을 저장하지 않기로 확정**되면서 규칙 단계를 제거했다 — 그 단계가 의존하던 입력이 실제로는 항상 빈 배열이라 영원히 아무것도 못 찾았을 것이기 때문이다. 지금은 사전집 항목의 `preferredForm`(선호 표기)과 `definition`(정의)만 갖고, 문서에 그 개념이 **리터럴 그대로 쓰였든 다른 말로 풀어썼든 전부 LLM 한 번의 호출로** 찾는다.

|---|---|---|---|
| `jobId` / `workspaceId` / `dictionaryVersionNo` | - | O | §3.1과 동일한 의미 |
| `dictionary` | array | O | 1개 이상. `ExistingTerm`(§3.1)을 **상속한** `DictionaryEntry`(termId/preferredForm/englishName/synonyms + `definition`). `ExistingTerm` 자체는 건드리지 않는다(§10 D-19). **`synonyms`는 실제로는 항상 빈 배열이다** — 실제 DB가 동의어를 저장하지 않기 때문이다(§10 D-22). 필드는 하위 호환을 위해 스키마에 남겨뒀을 뿐, 판정 로직은 이 필드를 보지 않는다 |
| `documents` | array | O | 1개 이상. **`DocumentInput`(§3.1)과 동일한 스키마** |

### 12.2 응답

```json
{
  "jobId": "0f2c1a3e-...",
  "status": "SUCCESS",
  "dictionaryVersionNo": 7,
  "suggestions": [
    {
      "termId": "t-001",
      "preferredForm": "구독자",
      "foundForm": "이용자",
      "documentId": "d-101",
      "department": "마케팅",
      "snippet": "이번 달 이용자 대상 혜택 안내드립니다",
      "charStart": 12,
      "charEnd": 15,
      "reason": "결제 실패로 인해 계정을 일시 중지한 상태를 가리킨다",
      "method": "llm"
    }
  ],
  "usage": { "model": "gemini-3.5-flash", "inputTokens": 4617, "outputTokens": 2091, "llmCalls": 1, "elapsedMs": 0 },
  "warnings": []
}
```

| 필드 | 규칙 |
|---|---|
| `termId` / `preferredForm` | `dictionary`에 있던 값 그대로 |
| `foundForm` | 문서에 **실제로 나타난 표기 그대로** — LLM이 짚어낸 문서 내 실제 부분 문자열(`matchedText`). 리터럴 그대로든 다른 말로 풀어쓴 문장이든, 반드시 문서 원문에 존재하는 문자열이어야 한다 |
| `charStart` / `charEnd` / `snippet` | §3.5 규칙 그대로 재사용 (0-based, end 미포함, 앞뒤 30자) |
| `reason` | 한 문장. 화면에 그대로 보인다 |
| `method` | 지금은 항상 `"llm"`이다(§10 D-22). 예전 규칙 단계의 흔적으로 필드는 남겨뒀다 |

`preferredForm` 자신이 문서에 정확히 그대로 등장한 경우는 제안하지 않는다 — 이미 올바른 표기다.

### 12.3 판정 방법 — LLM 단독, 정의 기반

`extract`의 SYNONYM/HOMOGRAPH 단계와 같은 원칙 — **LLM은 의미 판단만, 오프셋은 결정론적 코드가 계산**한다(§5 ③). 사전집 각 항목의 `preferredForm`·`definition`만 주고, 문서에 그 개념이 리터럴로 그대로 쓰였든 다른 말로 풀어썼든 **전부 한 번의 호출로** 찾게 한다(§10 D-22). LLM이 돌려준 `matchedText`를 코드가 문서에서 다시 찾아 실제 offset을 계산하고, 그 과정에서 세 가지를 방어적으로 검증한다:
1. `termId`가 요청의 `dictionary`에 실재하는가 — 아니면 버린다
2. `matchedText`가 해당 문서에 리터럴로 실제 존재하는가 — 아니면 버린다
3. `matchedText`가 `preferredForm`과 정확히 같지는 않은가 — 같으면 이미 올바른 표기라 버린다

`python -m app.cli contrast`가 이 호출을 실행한다. (예전엔 규칙 단계만 따로 보는 `--skip-llm` 옵션이 있었는데, LLM이 유일한 메커니즘이 된 지금은 의미가 없어져 제거했다.)

**HOMOGRAPH(주문·활성·정산·등급)는 사전집에 넣지 않는다** — "치환할 선호 표기"가 없는 별개 문제(부서마다 다른 뜻으로 고정하는 문제)라서다. 자세한 이유는 §10 D-19.

**사전집 규모가 커지면 재현율 개선 방식을 다시 설계해야 할 수 있다** — 알려진 확장성 제약과 분기점은 §10 D-29 참고(지금 13개 규모에서는 해당 없음).
