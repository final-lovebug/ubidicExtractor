# 02. 예외 처리

## 한 장 요약

**LLM의 출력도, 외부 API의 응답도 신뢰하지 않는다는 전제로 방어를 6계층 쌓았다. 핵심은 "무엇을 폴백하고 무엇을 즉시 실패시키는가"의 경계를 실측으로 정한 것이다.**

| 항목 | 값 | 근거 |
|---|---|---|
| 방어 계층 | 6종 (입력·응답·외부장애·폴백·비용·전파) | `SPEC.md` §6 |
| 환각 방어 검증 | 3종 (termId 실재 / matchedText 실재 / preferredForm 동일) | `SPEC.md` §12.3 |
| 실제 환각 발생 | **0건** (전 모델·전 회차) | → [01 §8](01-verification.md) |
| 호출 상한 | 프로세스당 20회 (초과 시 예외) | `AGENTS.md` |
| 폴백 단계 | 2단 (키 체인 → 모델 체인) | D-38·D-39·D-40 |

**가장 중요한 세 가지**
- 환각을 "프롬프트로 부탁"하지 않고 **코드가 검증해서 버린다** — LLM은 문자열만 답하고 좌표는 코드가 다시 찾는다. (→ §3)
- 폴백 조건은 추측이 아니라 실측으로 정했다 — 무효 키가 401이 아니라 **400**으로 온다는 걸 직접 찔러보고 알았다. (→ §5)
- 재시도해도 소용없는 것(404 오타, 400 스키마 오류)은 **일부러 즉시 실패**시킨다 — 조용히 넘어가면 진짜 버그를 "키 탓"으로 착각한다. (→ §5-3)

**여기에 없는 것**
5xx 상황에서 키를 전부 순회하는 경로는 실제 503을 강제할 방법이 없어 **코드 경로 확인으로만** 검증했다(D-40). 후퇴선(정밀도 0.70 미달 시 발동)은 설계돼 있으나 한 번도 발동하지 않았다 — 즉 실전 검증이 안 됐다.

**원본**: `SPEC.md` §6·§12.3·§8 · `AGENTS.md` LLM 호출 규칙 · §10 D-15·D-16·D-19·D-22·D-26·D-28·D-36·D-38~D-40 · `ubidict-py/task.md`

## 1. 전제 — LLM의 출력을 신뢰하지 않는다

이 시스템에서 LLM은 **"의미 판단"만** 한다. 그 외 전부는 코드가 한다.

| LLM이 하는 것 | 코드가 하는 것 |
|---|---|
| 이 표기들이 같은 개념인가 | 그 표기가 문서 어디에 있는지 좌표 계산 |
| 이 단어가 문맥마다 다른 뜻인가 | 몇 번 나왔는지 세기 |
| 이 문장이 사전집의 어느 용어를 말하는가 | 응답이 스키마에 맞는지 검증 |

**LLM이 만든 좌표(`charStart`/`charEnd`)를 그대로 쓰지 않는다**는 게 설계의 뿌리다. LLM이 돌려준 문자열을 코드가 원문에서 다시 찾아 좌표를 계산한다(D-5). 이 한 가지 결정이 §3의 환각 방어를 가능하게 만든다 — 문서에 없는 문자열은 애초에 좌표를 계산할 수 없으므로 자동으로 걸러진다.

## 2. 입력·계약 방어

### X-01 · JSON Schema 강제

`response_mime_type: "application/json"` + `response_schema`로 응답 구조를 모델에 강제한다.

> `AGENTS.md`: **JSON Schema** — `response_schema`로 강제. **응답을 정규식으로 파싱하는 코드를 쓰지 마라**

정규식 파싱을 금지한 이유는 실패 모드가 조용하기 때문이다 — 형식이 살짝 어긋나면 정규식은 "일부만 잘못 뽑아낸 결과"를 내놓고, 그게 그대로 채점에 들어간다. 스키마 강제는 어긋나면 파싱 단계에서 바로 터진다.

### X-02 · `temperature` 0~0.2 고정

> `AGENTS.md`: **올리지 마라** — 같은 입력에 같은 출력이 나와야 튜닝이 가능하다

판정 작업이라 창의성이 필요 없다. 다만 **0.1로 고정해도 모델에 따라 결과가 흔들린다**는 게 실측으로 확인됐다 — `3.1-flash-lite`는 5회 완전 동일, `3.5-flash-lite`는 회차마다 달랐다(D-24·D-25). 그래서 §X-02만으로는 재현성이 보장되지 않고, 5회 반복 측정이 필요했다(→ [01 §3-3](01-verification.md)).

### X-03 · 계약 고정

> `AGENTS.md`: **계약을 임의로 바꾸지 마라.** 다른 팀이 이미 그 스키마로 코드를 쓰고 있다

스키마 변경이 필요하면 **상속으로 확장**하고 기존 타입은 건드리지 않는다. §12에서 `definition` 필드가 필요했을 때 `ExistingTerm`을 수정하지 않고 `DictionaryEntry(ExistingTerm)`를 새로 만든 게 이 규칙의 적용 사례다(D-19, → [04 §5](04-improvements.md)).

## 3. 응답 방어 — 환각

§12는 LLM이 "사전집의 어느 용어가 문서의 어느 문구를 가리키는가"를 답하는 구조라, 모델이 **없는 용어 ID를 지어내거나 문서에 없는 문구를 만들어낼** 여지가 있다. 그래서 응답을 받은 뒤 코드가 3가지를 검증하고 실패하면 **그 매치를 버린다**.

| ID | 검증 | 실패 시 |
|---|---|---|
| **X-04** | `termId`가 요청의 `dictionary`에 실재하는가 | 버림 + 경고 |
| **X-05** | `matchedText`가 해당 문서에 리터럴로 실제 존재하는가 | 버림 + 경고 (환각 의심) |
| **X-06** | `matchedText`가 `preferredForm`과 정확히 같지는 않은가 | 버림 (이미 올바른 표기라 제안할 게 없음) |

X-04·X-05는 D-19에서, X-06은 D-22에서 추가됐다. X-06은 규칙 단계를 제거하면서 사라진 `if form == preferredForm: continue` 로직 중 **코드로 보장 가능한 부분만 되살린 것**이다.

### 버린 것을 조용히 버리지 않는다

버려진 매치는 콘솔에 즉시 찍히고, `logs/contrast_llm_call_details.jsonl`의 `droppedMatches`에 사유와 함께 구조화되어 남는다.

```
{termId, documentId, matchedText, reason}
```

사용량 로그에도 `matchesReturned` / `matchesAccepted` / `matchesDropped` 3개 필드가 따로 있다 — **`matchesDropped`가 0이 아니면 프롬프트를 더 다듬어야 한다는 신호**로 쓰기 위해서다.

**실측 결과: 전 모델·전 회차에서 `matchesDropped`는 0이었다.** 방어가 한 번도 발동하지 않았다는 뜻이고, 동시에 "이 방어가 실전에서 검증됐다"고는 말할 수 없다는 뜻이기도 하다.

## 4. 외부 장애

### X-07 · 5xx·타임아웃은 2회까지 지수 백오프

> `SPEC.md` §6: **재시도** — 5xx·타임아웃만 2회까지, 지수 백오프. 4xx는 재시도하지 않는다

키 하나당 최대 3회 시도(최초 1 + 재시도 2), 대기는 2초 → 4초.

### X-08 · 4xx는 재시도하지 않는다

4xx는 "요청이 잘못됐다"는 뜻이라 같은 요청을 다시 보내도 같은 답이 온다. 재시도는 시간과 쿼터만 쓴다.

**단, 4xx 중에도 "요청이 아니라 키의 문제"인 것이 있다** — 이 구분이 §5의 폴백 조건표다.

### 503을 만났을 때 — 일시적인가 지속적인가

같은 `503 UNAVAILABLE`이라도 대응이 달랐다.

| 사례 | 증상 | 판정 | 대응 |
|---|---|---|---|
| D-26 (§12, `3.5-flash`) | 5회 중 2회차에 1번 | **일시적 스파이크** | 즉시 재시도 → 바로 성공 |
| D-15·D-16 (`3.7`·`3.8-flash`) | 이틀에 걸쳐 5회 시도 전부 실패 | **지속적 용량 문제** | 측정 포기, 해당 모델 사용 중단 |
| D-28 (§12, `3.7-flash`) | 120초·180초 타임아웃 후 각각 503 | 위와 동일 증상 재확인 | 2회 연속 실패 후 중단 |

**판단 기준**: 재시도로 풀리면 일시적, 날짜를 바꿔도 안 되면 지속적. D-28이 의미 있는 건 **별도 기능·별도 모듈**(`contrast_llm.py`)에서 extract와 정확히 같은 증상이 나왔다는 것 — 우리 코드가 아니라 모델 쪽 문제라는 근거가 됐다.

**실패도 쿼터를 먹는다**는 게 중단 기준을 만들었다. `3.7`·`3.8-flash`는 2회 연속 실패하면 더 두드리지 않았다(D-15·D-28).

### X-09 · RPD 소진(`429 RESOURCE_EXHAUSTED`)은 재시도하지 않는다

D-36에서 `3.5-flash` 5회 측정 중 4회차가 `RESOURCE_EXHAUSTED`(`retryDelay 46s`)로 실패했다. **재시도하지 않고 실패를 그대로 기록했다** — 5회차가 같은 분 안에 성공한 걸 보면 일시적 스로틀링으로 보였지만, 원인을 단정하지 않았다.

이때 얻은 교훈이 하나 더 있다. 두 로그(extract+contrast)를 합산한 그날 실호출은 20에 한참 못 미쳤는데도 소진이 났다 — **"RPD 잔량 계산은 참고용이지 보장값이 아니다"**(→ [03 §B](03-troubleshooting.md)).

## 5. 폴백 — 키 체인과 모델 체인

호출 한 번은 3중 루프 안에서 일어난다.

```
모델 체인 (X-11)
 └─ 키 체인 (X-10)
     └─ 5xx 재시도 2회 (X-07)
```

### X-10 · API 키 순차 폴백 (D-38)

`GEMINI_API_KEY_1`, `_2`, … 를 1번부터 순서대로 쓴다. 번호 붙은 키가 없으면 기존 `GEMINI_API_KEY` 단수로 그대로 동작한다(마이그레이션 강제 없음).

**키 값은 절대 로그에 남기지 않는다** — 몇 번째 키였는지(`keyIndex`)만 남긴다.

### X-11 · 모델 체인 폴백 (D-39·D-40)

체인은 두 경로로 정해진다.
1. `--model`에 콤마로 나열 — 명시한 순간 `.env` 체인은 무시된다
2. `--model` 없이 실행 — `.env`의 `GEMINI_MODEL_1`, `_2`, …(없으면 단수 `GEMINI_MODEL`)

**체인 길이가 1이면 폴백 분기가 아예 실행되지 않는다.** 재현성 측정에서 `--model` 하나만 주는 기존 관행이 그대로 유지되도록 만든 설계다(→ [01 §11](01-verification.md)).

모델이 바뀌면 **키 폴백은 1번 키부터 다시 시작**한다.

### 5-3. 판정 조건표 — 무엇이 폴백이고 무엇이 즉시 실패인가

이 표가 이 문서에서 가장 중요한 산출물이다.

| 응답 | 판정 | 동작 | 근거 |
|---|---|---|---|
| `401` / `403` | 인증·권한 — 이 키의 문제 | 다음 키 | D-38 |
| `429` | 쿼터 소진 — 이 키의 문제 | 다음 키 | D-38 |
| `400` + `reason: API_KEY_INVALID` | 무효 키 — 이 키의 문제 | 다음 키 | **D-38 실측 정정** |
| `400` (그 외) | 프롬프트·스키마 문제 | **즉시 실패** | 키를 바꿔도 똑같이 실패 |
| `404` | 모델명 오타·설정 실수 | **즉시 실패** | **D-39 실측 확인** |
| `5xx` | 서버 문제 | 재시도 2회 → 다음 키 → 다음 모델 | **D-40 정정** |

**"무엇을 폴백하지 않기로 했는가"가 설계 의도를 더 잘 보여준다.**

- 일반 `400`을 폴백 대상에 넣으면, 프롬프트/스키마 버그가 생겼을 때 등록된 키를 전부 소진하며 같은 실패를 반복하고 마지막에 "전부 실패"라는 혼란스러운 에러만 남는다. **진짜 버그가 "키 탓"으로 위장된다.**
- `404`(존재하지 않는 모델)를 폴백시키면 `.env`의 모델명 오타를 조용히 다음 모델로 넘겨버려, 잘못된 설정으로 계속 돌아가는 걸 아무도 모른다.

세 줄이 **실측으로 정정된 것**이다 — 계획 단계에서 추측했던 것과 실제가 달랐다. 그 경위는 [03 §E](03-troubleshooting.md)에 있다.

### 5-4. 폴백해도 안 되면

체인을 전부 소진하면 **마지막 예외를 그대로 올려보낸다.** 삼키거나 빈 결과로 대체하지 않는다.

## 6. 비용·폭주 안전장치

### X-12 · 응답 캐시

`sha256(모델명 + 프롬프트)` → `.cache/{hash}.json`. 채점·후처리 코드를 고칠 때 API를 다시 부르지 않는다. `--no-cache`로 무시할 수 있다.

**캐시 키에 모델명이 들어간다**는 게 중요하다 — 처음엔 프롬프트만 해싱해서, 모델만 바꿔 돌리면 이전 모델의 캐시를 새 모델 결과로 착각할 수 있는 상태였다(→ [03 §B](03-troubleshooting.md), D-11).

### X-13 · 프로세스당 호출 상한 20회

> `AGENTS.md`: **호출 상한** — 한 프로세스에서 20회. 넘으면 예외를 던지고 중단한다

루프 사고로 요금이 나가는 것을 막는 장치다. 카운터는 캐시 히트를 세지 않는다(실제 API를 안 불렀으므로).

### 최악의 호출 수 — 폴백이 늘린 위험

폴백 2단이 생기면서 **한 번의 논리적 호출이 최대 `모델 수 × 키 수 × 3`회**의 실제 API 호출이 될 수 있다(3 = 최초 1회 + 5xx 재시도 2회).

현재 설정(모델 4 × 키 4)이면 최악 **48회** — `MAX_LLM_CALLS=20`을 넘는다. 키나 모델을 늘릴 때마다 이 여유를 같이 확인해야 한다는 걸 D-38·D-40에 경고로 적어뒀다.

## 7. 실패를 숨기지 않는다

| 장치 | 내용 |
|---|---|
| `status` | `SUCCESS` / `PARTIAL`(일부만 성공, 사유는 `warnings`) / `FAILED`(빈 결과 + 사유) |
| `warnings` | `--skip-llm` 사용, stub 모드 등 "정상이지만 알아야 할 것" |
| `keyIndex` / `modelIndex` | 몇 번째 키·모델로 성공했는지 (기본값 1이면 표시 안 함) |
| `droppedMatches` | 버려진 환각 매치와 그 사유 |
| 실패 전파 | 서비스 레이어는 예외를 삼키지 않는다 — HTTP는 502, 큐 컨슈머는 메시지를 삭제하지 않음 |

`AGENTS.md`의 원칙이 이 장치들의 근거다.

> 그래도 안 되면 **그 사실을 그대로 보고하라.** … **숫자를 꾸미지 마라.**

## 8. 프로덕션에서 추가된 방어 (`ubidict-py/`)

R&D(`test/`)에는 없던, 큐 기반 서비스라서 필요해진 것들이다.

### X-14 · 멱등성 — 중복 배달 방어

SQS 표준 큐는 **"최소 한 번(at-least-once)" 전달**이라 같은 메시지가 두 번 올 수 있다. 같은 작업을 두 번 처리하면 Gemini 비용이 두 배가 되고 백엔드에 중복 응답이 간다.

MySQL 테이블 하나(`processed_jobs`)로 막는다. **순서가 핵심이다.**

```
처리 → 응답 큐 발행 → 멱등성 기록 → 메시지 삭제
```

기록을 먼저 하면, 기록 직후 죽었을 때 "처리 안 했는데 처리한 걸로" 영구히 남아 그 작업이 다시는 처리되지 않는다(백엔드가 응답을 영영 못 받음). 순서를 지키면 최악의 경우도 "응답이 중복 발행될 수 있다" 정도다 — **알려진 트레이드오프로 기록해뒀다.**

멱등성 확인 자체가 실패하면(MySQL 다운 등) **메시지를 삭제하지 않는다** — 중복 처리 위험보다 유실 위험이 크다고 판단했다.

### X-15 · DLQ

요청 큐에 `maxReceiveCount=3`으로 DLQ(`lovebug-llm-dlq`)가 연결돼 있다. 처리 실패 시 메시지를 삭제하지 않으므로, 3회 반복 실패하면 DLQ로 격리된다.

**알려진 한계**: 지금은 실패할 때마다 매번 `FAILED` 응답을 발행한다 — 재시도마다 중복 발행될 수 있어, 백엔드가 "가장 최근 상태만 신뢰"하도록 처리해야 한다. 백엔드 팀과 확정이 필요한 항목이다.

### X-16 · stub / real 모드

요청의 `mode` 필드로 고른다. `stub`(기본값)이면 **DB·Gemini를 아예 부르지 않고** 2.5초 뒤 빈 결과를 돌려준다. 백엔드가 큐·폴링 배선만 검증하고 싶을 때 비용 없이 쓰라고 만든 것이고, 기본값을 `stub`으로 둔 건 **명시하지 않으면 비용이 안 나가게** 하기 위해서다.

### X-17 · 읽기 전용 접근 원칙

`app/backend_db.py`는 백엔드 소유 테이블(`document`·`document_version`·`term`)을 **읽기만** 한다. `extraction_job`·`check_job` 같은 상태 테이블은 이미 존재하지만 여기서 갱신하지 않는다 — 처리 결과는 응답 큐로만 돌려주고, 상태 갱신은 백엔드가 자기 책임으로 한다.

운영에서는 **읽기 전용 DB 계정**을 따로 만드는 게 안전하다(쓰기 권한 자체가 없으면 사고가 원천 차단된다) — 아직 적용 전이다.

## 9. 후퇴선 — 발동하지 않았다

> `SPEC.md` §8: 정밀도가 0.70에 못 미치면 `02_forbidden.md`에 규칙을 추가하고 다시 채점한다. **세 번 시도해도 못 넘으면 `confidence` 임계값을 0.5에서 0.7로 올려** 재현율을 희생하고 정밀도를 확보한다. 그래도 안 되면 그 사실을 그대로 보고하라 — 제품 설계에 **"정밀도 0.7 미만이면 대조를 필수가 아니라 경고로 내린다"**는 후퇴선이 이미 준비돼 있다.

**한 번도 발동하지 않았다.** 정밀도는 4단계 첫 호출부터 1.00이었고(D-4·D-6), 전 기간 통틀어 0.83 아래로 내려간 적이 없다(→ [01 §8-4](01-verification.md)).

발동하지 않았다는 건 좋은 소식이지만, 동시에 **이 후퇴선이 실전에서 검증되지 않았다**는 뜻이기도 하다.

## 10. 아직 방어하지 않는 것

- **5xx에서의 키 순회 실측.** 실제 503을 강제할 방법이 없어 코드 경로 확인으로만 검증했다(D-40).
- **환각 방어 3종의 실전 검증.** `matchesDropped`가 전 기간 0건이라 "버리는 경로"가 실제로 도는 걸 못 봤다.
- **후퇴선.** 위와 같은 이유.
- **키별 RPD 잔량 추적.** 지금 RPD 계산은 모델 기준이라 어느 키가 얼마나 남았는지 모른다 — "막히면 다음 키로" 이상으로는 안 만들었다(D-38).
- **`MAX_LLM_CALLS`와 폴백 최악값의 충돌.** 모델 4 × 키 4면 최악 48회로 상한 20을 넘는다. 경고만 적어뒀고 코드로 막지는 않았다.
- **FIFO 큐.** 설계 문서는 FIFO + `MessageGroupId`를 말하는데 실제 프로비저닝된 큐는 표준 큐다. FIFO로 바뀌면 `send_message`에 파라미터 추가가 필요하다.
