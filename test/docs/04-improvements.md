## 1. 개입의 원칙

`AGENTS.md`가 정한 규칙이 모든 개선의 전제다.

> **필요성이 증명되기 전엔 복잡도를 늘리지 마라.** 형태소 분석기·임베딩 클러스터링을 넣지 마라 — 후보가 수백 개가 된 뒤에.

그래서 이 프로젝트의 개선은 전부 **"실측으로 부족한 게 확인된 다음에"** 일어났다. 순서는 항상 같았다.

```
골드셋으로 잰다 → 못 넘긴 항목을 본다 → 가장 싼 수단부터 쓴다 → 다시 잰다
```

**가장 싼 수단의 순서**: 프롬프트 문구 → 금지 규칙 추가 → 응답 스키마 구조 → 모델 교체 → 코드 추가. 실제로는 **뒤로 갈수록 효과가 컸다**는 게 아이러니다.

## 2. 튜닝 루프와 그 한계

`SPEC.md` §8이 설계한 루프는 이랬다.

> 정밀도가 0.70에 못 미치면 `02_forbidden.md`에 규칙을 추가하고 다시 채점한다. 세 번 시도해도 못 넘으면 `confidence` 임계값을 0.5에서 0.7로 올린다.

### I-01 · 이 루프는 거의 돌지 않았다 (D-4)

정밀도가 **첫 실제 호출부터 1.00**이었다. `02_forbidden.md`에 **한 줄도 추가할 필요가 없었다** — `01_role.md`의 기본 4개 규칙만으로 3회 호출 모두 오탐이 0이었다.

**루프가 안 돌았다는 건 좋은 소식이지만, 동시에 그 루프가 검증되지 않았다는 뜻이다.** 나중에 실제로 오탐이 나왔을 때(E-03) 비로소 이 파일에 처음 한 줄이 들어갔다.

### 문제는 정밀도가 아니라 재현율이었다

설계된 루프는 **정밀도**를 고치는 장치였는데, 실제로 막힌 건 **재현율**이었다 — 특히 HOMOGRAPH `G6`("주문").

| 시도 | 방법 | 결과 |
|---|---|---|
| 1~3차 (D-7) | 프롬프트 **문구** 수정 (예시 교체, 일반 지침 추가) | 후보로도 안 나옴 |
| 4차 (D-9) | **구조** 변경 — 고빈도 힌트 + 사고 유도 스키마 | **후보에는 들어옴**, 최종에서 탈락 |
| 5차 (D-10) | 판별 **질문** 추가 ("가리키는 것의 개수가 부서마다 다른가") | 또 탈락 |
| 6차 (D-11) | **모델 교체** (`3.5-flash-lite`) | 실패 + **오탐 발생**(퇴보) |
| 7차 (D-12) | 금지 규칙 한 줄 추가 | **성공** — 그러나 재현율 20% (D-13) |
| 8차 (D-14) | **모델 교체** (`3.5-flash`) | **5회 연속 성공** |

**D-9가 전환점이었다.** 그 전까지는 "모델이 '주문'을 쳐다보지도 않는다"가 가설이었는데, 사고 유도 스키마를 넣자 `consideredHomographCandidates`에 "주문"이 **실제로 들어왔다.** 최종 답에서는 여전히 빠졌지만, 문제가 **"주의(attention)"에서 "판단 기준"으로 좁혀졌다.**

### I-02 · 프롬프트 튜닝을 멈춘 것이 개선이었다 (D-10 → D-14)

5회 실패 후 D-10에 이렇게 적었다.

> 이제는 우연이 아니라 **이 모델이 가진 안정적인 판단 성향**으로 보는 게 타당하다 — 프롬프트를 더 다듬어서 해결될 확률이 앞의 시도들보다 낮아 보인다. **(에이전트 권장: 프롬프트 튜닝은 여기서 멈춘다.)**

그리고 모델을 바꿨더니 `G6`가 **5회 전부 성공**했다.

**배운 것.** "모델이 이 개념을 다루는 능력 자체가 없는" 경우와 "프롬프트가 부족한" 경우는 다르다. 전자는 프롬프트로 못 고친다. **판별법은 재현성이다** — 매번 같은 것을 놓치면 능력 문제(D-24가 §12에서 같은 결론을 냈다), 회차마다 다른 걸 놓치면 프롬프트·온도 문제.

> **발표 소재.** 프롬프트 튜닝 5회 실패를 "더 열심히"로 대응하지 않고, 실패 패턴을 근거로 "이건 프롬프트로 안 되는 것"이라고 판정한 뒤 다른 축(모델)으로 옮겨 해결했다.

## 3. 사고 유도 스키마 — 이 프로젝트의 핵심 기법

### I-03 · 발명 (D-9, HOMOGRAPH)

**아이디어.** `response_schema`에서 **추론 필드를 답변 필드보다 먼저 선언**한다.

```
LlmExtractionResult:
  consideredHomographCandidates: list[str]   ← 먼저
  homographs: list[Homograph]                ← 나중
```

프롬프트에는 "먼저 참고 목록에서 10~15개를 골라 `consideredHomographCandidates`에 담고, **그 각각을 실제로 재검토한 뒤에만** `homographs`에 담아라"고 절차를 명시한다.

**왜 되는가.** LLM은 토큰을 순서대로 생성한다. 답을 쓰기 전에 후보를 나열하게 만들면 **나열하는 행위 자체가 컨텍스트가 되어** 이후 판정에 영향을 준다. "생각해봐라"라고 부탁하는 게 아니라 **스키마가 강제한다.**

**당시 결과.** HOMOGRAPH에서는 `G6`를 최종 답으로 끌어내지 못했다. **그래도 남겨뒀다** — 후보 인식 범위가 실제로 넓어졌고(`G15`까지 들어왔다), 무엇보다 **모델이 무엇을 검토했는지 로그로 볼 수 있게 된 것**이 진단 도구로 값졌다.

### I-04 · 이식 (D-30~D-33, §12) — 여기서 효과가 터졌다

§12(사전집 대조)의 재현율이 낮아(→ [03 E-10](03-troubleshooting.md)) 개선이 필요해졌을 때, **새 기법을 발명하지 않고 D-9의 것을 그대로 가져왔다.**

```
LlmContrastResult:
  consideredTermIds: list[str]   ← 사전집 termId를 하나도 빠짐없이 전부
  matches: list[...]             ← 그중 실제로 있다고 판단한 것만
```

**결과 — 4개 모델 중 3개에서 재현율이 올랐다.**

| 모델 | 변화 | 특기사항 |
|---|---|---|
| `3.1-flash-lite` | 0.42 → 0.63 | 가장 큰 폭 |
| `3.5-flash-lite` | 0.50 → 0.61 | **변동폭이 크게 줄었다** — 평균보다 이쪽이 더 값지다 |
| `3.5-flash` | 0.89 → 0.95 | 5회 중 1회는 26/26 만점 |
| `3.6-flash` | 0.92 → 0.89 | **유일한 하락** |

*(회차별 상세는 [01 §8](01-verification.md))*

**같은 모델, 같은 프롬프트 골격, 오직 "판정 전에 전부 검토했다는 걸 스키마로 강제"한 것만 바꿨다.** `consideredTermIds` 로그를 열어보니 13개 termId가 매번 빠짐없이 채워져 있어 강제가 의도대로 작동했다.

**트레이드오프도 기록했다.** `3.1-flash-lite`는 적용 전 5회 완전 동일(완전한 결정론)이었는데 적용 후 ±1건 흔들리게 됐다. 평균이 크게 올라서 남는 장사로 판단했지만, **재현성을 일부 내주고 재현율을 산 것**이다.

**`3.6-flash`의 하락은 숨기지 않았다.** 4개 중 3개에서 개선됐다고 쓰지, "효과가 검증됐다"고 쓰지 않는다.

> **발표 소재.** 한 기능(HOMOGRAPH)에서 "실패"로 끝났던 기법이, 다른 기능(사전집 대조)에서 재현율을 크게 끌어올렸다. 실패한 시도를 지우지 않고 남겨뒀기 때문에 재사용할 수 있었다.

### I-05 · 고빈도 힌트 (D-8 → D-9)

D-9의 사고 유도 스키마와 짝을 이루는 장치다. 문서에서 "여러 부서에 걸쳐 반복 등장하는 짧은 명사"를 뽑아 프롬프트에 참고 목록으로 넣는다(`find_frequent_terms()`).

**설계 과정 자체가 기록할 만하다.** 처음엔 VARIANT의 후보 추출기(`_extract_candidate_forms`)를 재사용하려 했는데, 그게 **마크다운 강조(`**볼드**`·`` `코드` ``) 스팬만 본다**는 걸 그때 발견했다(D-8). 실제 프로덕션 문서가 강조 없이 평문이면 아무것도 못 찾는 구조적 한계다.

**그래서 재사용하지 않고 공백 기반으로 새로 설계했다** — 어절을 공백으로 나누고 조사·용언 종결(`-다`)을 제거한 뒤, 3개 이상 문서에 걸쳐 나오는 2~4음절 표기를 뽑는다. 마크다운에 의존하지 않는다.

**아이러니한 발견.** 규칙 기반(VARIANT)이 LLM 기반(SYNONYM/HOMOGRAPH)보다 **문서 스타일에 더 취약하다.** LLM 쪽은 문서 원문 전체를 프롬프트에 넣으므로 강조 여부와 무관하다.

**D-21에서 같이 기록한 경고.** LLM 단계가 골드셋에 없는 매치 2건을 추가로 찾았는데, 원인이 **"문서에 정의 문장을 거의 그대로 반복해서 쓴 것"**으로 보였다. 틀린 결과는 아니지만 **골드셋 문서가 LLM에게 너무 쉬우면 측정이 낙관적으로 나온다.** 실제 서비스 문서는 정의를 이렇게 되풀이하지 않을 가능성이 높다.

## 7. 만들지 않기로 한 것 — 6건

**안 만든 이유와 "언제 다시 볼지"를 같이 적어두지 않으면, 나중에 누군가 같은 고민을 처음부터 다시 한다.**

| # | 안 만든 것 | 이유 | 다시 볼 분기점 |
|---|---|---|---|
| 1 | §12 **2단계 후보 필터링** (D-29) | 사전집 13개에서는 리스크가 이론적. 사전집이 커지면 `consideredTermIds` 나열이 오히려 주의력을 분산시켜 재현율을 **떨어뜨릴 수** 있다 | 사전집 **50개 초과** 또는 실측으로 재현율 하락·토큰 급증 확인 |
| 2 | VARIANT **공백 기반 후보 발견** (D-8) | 픽스처 문서 기준으로는 통과 중. 실제 문서로 테스트할 근거가 아직 없다 | **실제 팀 문서**에서 VARIANT 재현율이 낮게 나오는 시점 |
| 3 | 동형이의 충돌에 **LLM 문맥 판단** 추가 (D-18) | "등급" 같은 짧고 다의적인 동의어가 리터럴 매칭에 걸리는 건 본질적 한계. 실제 사전집에서 얼마나 자주 나오는지 모른다 | 실제 데이터에서 이 오탐 빈도가 확인되는 시점 |
| 4 | **라운드로빈** 키 분배 (D-38) | 순차 폴백은 "1번 키를 다 쓰고 2번으로"라 **RPD 소진 시점 예측이 쉽다.** 라운드로빈은 부하는 고르지만 모든 키가 동시에 바닥나고, 키별 잔량 추적이 필요해 복잡도가 는다 | 단일 키 RPM 한도가 병목이 되는 시점(동시 처리량이 늘 때) |
| 5 | `synonyms` **필드 제거** (D-22) | 하위 호환. 다른 팀이 이미 이 스키마로 코드를 쓰고 있을 수 있다 | 백엔드와 계약을 재확정하는 시점 |
| 6 | **형태소 분석기·임베딩 클러스터링** (`AGENTS.md`) | 정규화 + 리터럴 매칭으로 골드셋을 통과하고 있다 | 후보가 수백 개가 되는 시점 |

**4번(라운드로빈)은 사용자가 리스크 분석을 먼저 요구해서 결정된 건이다.** 두 방식의 리스크를 나란히 놓고 비교한 뒤 순차 폴백을 골랐고, **확장성 제약을 D-38에 명시적으로 남겼다** — "나중에 필요해지면 `api_keys.py`의 선택 전략만 갈아끼우면 된다"는 것까지 포함해서.

## 9. R&D → 프로덕션 (`ubidict-py/`)

### 그대로 옮긴 것

`app/pipeline/` 전체(`normalize`·`variant`·`synonym`·`llm`·`contrast_llm`·`api_keys`·`model_chain`·`usage_log`), `app/schema.py`, `prompts/` 8개. **검증된 코드를 "정리"하겠다고 손대지 않았다** — ruff 스타일 경고가 나왔을 때도 코드가 아니라 룰셋을 조정했다(→ [03 E-22](03-troubleshooting.md)).

### 뒤집힌 것

| R&D (`test/`) | 프로덕션 (`ubidict-py/`) | 왜 |
|---|---|---|
| Typer CLI | FastAPI + SQS 컨슈머 | 진입점만 바뀌고 파이프라인은 동일 |
| `normalize.py`의 픽스처 로더 | 제거 | 프로덕션은 DB에서 읽는다 |
| 문서를 요청 본문으로 받음 | **문서 ID를 받아 DB에서 직접 조회** | 본문 크기 문제 + 백엔드가 이미 갖고 있는 데이터를 다시 보낼 이유가 없다 |
| `--model` 플래그 | `.env`의 `GEMINI_MODEL_1..N` 체인 | 사용자가 매번 지정하지 않아도 폴백이 돌아야 한다 (D-40) |
| 결과를 `out/`에 파일로 | 응답 큐로 발행 | |

### 새로 생긴 것

멱등성(`processed_jobs`), 큐 봉투 스키마(`queue_schema.py`), 작업 요청 스키마(`job_schema.py`), `backend_db.py`(읽기 전용), stub/real 모드, `Dockerfile`, GitHub Actions CI/CD(ruff + pytest → ECR + CodeDeploy), 23개 테스트.

### 과거 문서를 왜 안 고쳤나

`SPEC.md`의 D-1~D-40은 **각 시점에 실제로 내린 판단의 기록**이다. 나중에 뒤집힌 것(D-12 → D-13, D-19의 규칙 단계 → D-22의 삭제)도 **원문을 남기고 정정을 덧붙였다.**

과거 기록을 지금 시점의 결론으로 고쳐 쓰면 **"왜 그렇게 하게 됐는지"가 사라진다.** 재현성 확인을 5회씩 하는 이유는 D-13에 있는데, D-12를 지우면 D-13도 맥락을 잃는다. `AGENTS.md`의 "숫자·기록을 꾸미지 마라"를 문서 자체에도 적용한 것이다.

같은 이유로 **이번 문서 세트를 만들면서도 원본을 고치지 않았다.** 원본과 어긋나는 부분 3건은 [README](README.md)에 각주로만 남겼다.
