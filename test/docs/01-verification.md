## 한 장 요약

**채점표(골드셋)를 코드보다 먼저 만들고, 모든 판정을 그 표로 채점했다. 모델 4종을 각각 5회씩 반복 측정해 "한 번 잘 나온 것"과 "매번 잘 나오는 것"을 구분했다.**

| 항목 | 값 | 근거 |
|---|---|---|
| 골드셋 | extract 25행(정답 15·함정 10) / contrast 38행(정답 26·함정 12) | `fixtures/gold.csv`, `fixtures/contrast/gold.csv` |
| 모델 비교 | 4종 × 5회, extract·contrast 각각 별도 | D-24~D-27, D-30~D-37 |

| 오탐 | 전 기간 3회, 전부 같은 함정(N1)·전부 `-lite` 계열 | D-11, D-13, D-35 |

**가장 중요한 세 가지**
- 검증은 3층이다 — 결정론적 대조(오프셋) → 골드셋 채점(정밀도·재현율) → 5회 반복(재현성). (→ §3)
- "5회 반복"은 처음부터 있던 규칙이 아니라, 1회 성공을 성공으로 착각할 뻔한 사건(D-13) 이후 생겼다. (→ §3-3)

**여기에 없는 것**
실제 팀 문서에서의 성능은 측정하지 못했다(픽스처는 함정을 의도적으로 심은 합성 문서다). `G6`("주문")은 프롬프트로 끝내 풀리지 않았고 모델 교체로 우회했다 — 11회 실패 기록은 [04 §2-3](04-improvements.md)에 있다.

## 1. 검증 철학 — 채점표를 코드보다 먼저 만들었다

LLM 판정은 "돌려보고 눈으로 확인"하면 통과 여부가 사람 기분에 따라 달라진다. 그래서 순서를 뒤집었다.

1. **정답과 함정을 먼저 정한다** — `fixtures/gold.csv`에 무엇이 정답이고 무엇이 묶이면 안 되는지 먼저 적는다.
2. **팀이 그 표에 동의한다** — `TEST-CHECKLIST.md` B-2·B-3에서 정답 15개·함정 10개를 사람이 검토하고 합의한다.
3. **그 다음에 판정 코드를 짠다.**
4. **골드셋은 점수를 맞추려고 고치지 않는다** — `AGENTS.md` "하지 말 것"에 명시. 골드셋이 틀렸다고 판단되면 고치지 말고 근거를 보고한다.

4번이 핵심이다. 채점표를 고칠 수 있으면 어떤 점수든 만들 수 있다. 실제로 이 규칙 때문에 `G-16`("타겟 유저")처럼 여러 모델이 반복해서 놓치는 항목도 **고치지 않고 "재검토 후보"로 기록만 해뒀다**(D-32) — 판정이 필요하면 사람이 한다.

## 2. 골드셋 설계 — 정답과 함정을 같이 심는다

### 2-1. extract 골드셋 (`fixtures/gold.csv`, 25행)

| 종류 | 개수 | ID | 판정 방식 |
|---|---|---|---|
| SYNONYM | 7 | G1·G2·G3·G8·G9·G10·G11 | LLM |
| VARIANT | 4 | G4·G5·G12·G13 | 규칙(정규화) |
| HOMOGRAPH | 4 | G6·G7·G14·G15 | LLM(문맥) |
| NEGATIVE(함정) | 10 | N1~N10 | 묶으면 오답 |

`NEGATIVE`는 실제 API 응답의 `kind`에 존재하지 않는다 — 채점 전용이다.

### 2-2. 함정이 정밀도를 재는 장치다

함정 10개는 "그럴듯하지만 묶으면 안 되는" 쌍이다.

| 함정 | 쌍 | 묶으면 안 되는 이유 |
|---|---|---|
| N1 | 결제 취소 / 환불 | 조건이 다름 — 승인 전 철회 vs 승인 후 반환 |
| N2 | 관리자 / 운영자 | 역할이 다름 |
| N3 | 결제 / 결제 수단 | 상위–하위 관계 |
| N4 | 이용자 / 타겟 유저 / User | 이미 사전집에 등재됨 |
| N5 | pg_error | 이미 등재됨 |
| N6 | 구독 / 구독료 | 개념과 금액 |
| N7 | 알림 / 공지 | 대상이 다름 |
| N8 | 구독 갱신 / 구독 연장 | 주체가 다름 |
| N9 | 결제일 / 결제월 | 편집거리 함정 |
| N10 | 반품 / 환불 | 절차가 다름 |

`N9`는 특별히 **규칙을 겨냥해 심은 함정**이다. 초기 VARIANT 규칙이 "정규화 후 편집거리 ≤ 1"이었는데 `결제일`/`결제월`이 정확히 여기 걸려 잘못 묶였다. 이 함정 하나가 규칙을 좁히게 만들었다(→ [03 §A](03-troubleshooting.md), D-1).

> **발표 소재.** 함정을 심은 골드셋이 코드가 아니라 *규칙 설계*의 오류를 잡아낸 사례다 — 정답만 있는 골드셋이었다면 `N9`는 영원히 안 보였다.

### 2-3. §12 contrast 골드셋 (`fixtures/contrast/gold.csv`, 38행)

정답 26행(`G-1`~`G-26`) + 함정 12행(`N-1`~`N-12`). 채점 표기의 분모 `/26`은 정답 행 수를 뜻한다.

extract와 **완전히 분리**돼 있다 — 픽스처·골드셋·로그·채점 로직 전부 별개다(D-17·D-20). 두 기능은 같은 모델을 써도 순위가 달라지기 때문에(→ §8-3) 섞으면 안 된다.

문서는 2장이다.
- `d-201` `9월_CS_이슈_노트.md` — 사람이 19개 절로 직접 구성(D-21)
- `d-202` `주간 운영 이슈 및 지표 점검 리포트.md` — **Gemini에게 프롬프트를 주고 생성**시킨 뒤, 사람이 내용을 감사해서 골드 행을 붙였다(D-23). 직접 쓴 문서만으로는 "정해진 것을 테스트하게 된다"는 우려 때문이었다.

## 3. 3층 검증 구조

이 프로젝트의 방법론 자체다. 아래로 갈수록 느리고 비싸지만, 위 계층이 통과해도 아래에서 뒤집힐 수 있다.

### 3-1. 결정론적 계층 — 좌표가 맞는가

`verify-offsets`가 `result.json`의 모든 `occurrence`에 대해 `content[charStart:charEnd]`를 실제로 잘라 `form`과 글자 단위로 비교한다. 하나라도 어긋나면 exit 1.

LLM 판정이 맞았는지와 **무관하게** 통과해야 하는 계층이다. 백엔드가 이 좌표로 문서에 하이라이트를 칠하므로 한 글자만 밀려도 엉뚱한 곳이 칠해진다.

실측: 2단계에서 전체 통과(D-5), §12 C-1에서 8건, C-3에서 **109건**(규칙 107 + LLM 2), D-22 전환 후 23건 — 전부 일치(D-18·D-19·D-22).

**LLM이 만든 좌표를 쓰지 않는다**는 설계가 이 계층을 가능하게 한다. LLM은 "어떤 문자열이 후보인가"만 답하고, 좌표는 코드가 원문에서 다시 찾아 계산한다(D-5).

### 3-2. 채점 계층 — 골드셋 대비 정밀도·재현율

`score`(extract) / `score-contrast`(§12)가 골드셋과 대조한다. 판정은 4가지다.

| 판정 | 뜻 |
|---|---|
| 완전 일치 | 골드 행의 `forms`를 전부 찾음 |
| 부분 일치 | 일부만 찾음 (예: `G11`의 두 표기 중 하나만) |
| 누락 | 하나도 못 찾음 |
| 오탐 | 함정(`N*`)의 `forms`를 **전부** 묶어냈을 때만 |

오탐 판정을 "전부 묶었을 때만"으로 한 이유가 있다. 부분 겹침으로 세면 정상 후보가 함정으로 오인된다 — 예를 들어 `N3`(결제/결제 수단)에 대해 `결제 수단`+`결제수단`만 묶은 정상 후보 `G5`는 `결제`를 포함하지 않으므로 오탐이 아니다.

정밀도 = 찾은 것 ÷ (찾은 것 + 오탐), 재현율 = 찾은 것 ÷ 전체 정답. **부분 일치는 "찾은 것"에 포함한다** — 다만 표에서는 완전/부분을 따로 세서 감춰지지 않게 한다.

### 3-3. 재현성 계층 — 왜 1회가 아니라 5회인가

이 계층은 **처음부터 있던 게 아니다.** 사건이 만들었다.

D-12에서 `G6`("주문") 검출에 처음 성공했다. 금지 규칙 한 줄을 추가한 직후였고, senses 2개까지 정확히 나왔다. 성공으로 기록할 뻔했다.

그런데 같은 프롬프트를 `--no-cache`로 3~4회 더 돌려봤더니 — **5회 중 1회만 성공(20%)**이었다. 게다가 재현 3회차에서는 D-12에서 금지 규칙을 추가했던 바로 그 오탐이 재발했다(D-13).

이후 **모든 모델 비교는 5회 반복**이 원칙이 됐다. `temperature`를 0.1로 고정해도 모델에 따라 결과가 흔들린다는 게 실측으로 확인됐기 때문이다(→ §8-2).

> **발표 소재.** "한 번 성공"과 "매번 성공"은 다르다 — 1회 결과를 성공으로 기록했다면 신뢰할 수 없는 모델을 채택했을 것이다(D-13).

## 6. 사람이 정하는 것과 에이전트가 정하는 것의 경계

검증의 신뢰성은 "무엇을 하지 않았는가"가 떠받친다.

**에이전트가 하지 않기로 못 박은 것** (`AGENTS.md` "하지 말 것")
- 골드셋을 고쳐서 점수를 맞추지 않는다
- 테스트 문서를 임의로 고치지 않는다(함정이 의도적으로 심어져 있다)
- 계약(§3 스키마)을 임의로 바꾸지 않는다 — 다른 팀이 이미 그 스키마로 코드를 쓰고 있다
- 임베딩 클러스터링·형태소 분석기를 근거 없이 넣지 않는다

**사람에게 물어야 하는 것** (`TEST-CHECKLIST.md` E표)

| 증상 | 사람이 정할 것 |
|---|---|
| 골드셋 정답이 이상해 보인다 | 고치게 두지 않는다 — 팀이 판단 |
| 정밀도가 세 번 시도 후에도 미달 | 후퇴선(경고 등급)을 발동할지 |
| 컨텍스트 한계 초과 | 문서를 줄일지, 부서별로 나눠 호출할지 |
| 계약에 없는 필드가 필요해 보인다 | 백엔드 담당과 함께 결정 |
| 임베딩·형태소를 넣으려 한다 | 채점으로 재현율 부족이 확인되기 전에는 막는다 |

**실제로 지켜졌다는 증거**
- D-7: `G6`을 못 찾자 "정답을 프롬프트에 박아 넣는" 방법을 검토했으나 **의도적으로 하지 않았다** — 채점이 무의미해지기 때문. 대신 미해결로 남기고 팀 판단을 기다렸다.
- D-7·D-9·D-10은 전부 "팀 판단 대기"로 끝난다.
- `guide/decisions-log.md`에는 채점기가 판정할 수 없는 **제품 의미 판단**("주문"을 어느 팀 정의로 통일할 것인가)이 따로 기록돼 있다.
- D-22·D-40은 **사용자가 설계 허점을 지적해 뒤집힌** 사례다(→ [03 §C](03-troubleshooting.md)).

## 9. 측정 예산 — 쿼터가 실험 설계를 바꿨다

| 모델 등급 | RPM | TPM | **RPD** |
|---|---|---|---|
| `*-flash-lite` (3.1) | 30 | 1,000,000 | **1,500** |
| `*-flash-lite` (3.5) | 30 | 250,000 | **1,500** |
| `*-flash` (3.5~3.8) | 5 | 250,000 | **20** |

`flash` 계열의 RPD 20은 `flash-lite`의 **1/75**다(D-14). "5회 반복"이라는 원칙은 이 한도 안에서 나온 타협이다 — 하루에 최대 4개 모델 × 5회면 20회로 정확히 한도를 채운다.

이 제약이 실제로 만든 결정들:
- `3.7`·`3.8-flash`는 503이 2회 연속 나오면 **더 두드리지 않고 중단**했다 — 실패도 쿼터를 먹기 때문(D-15·D-28).
- extract와 §12가 **같은 모델을 쓰면 RPD를 공유**하므로, 사용량 확인은 두 로그를 합산해서 본다(D-20, `_today_real_calls_combined()`).
- 응답 캐시(`sha256(model + prompt)`)로 채점·후처리 코드를 고칠 때는 API를 다시 부르지 않는다. 캐시 키에 모델명이 빠져 있던 버그가 여기서 나왔다(→ [03 §B](03-troubleshooting.md), D-11).
- D-36에서는 계산상 여유가 있는데도 RPD가 소진됐다 — **"RPD 잔량 계산은 참고용이지 보장값이 아니다"**(→ [03 §B](03-troubleshooting.md)).

컨텍스트 예산은 반대로 여유로웠다. 문서 5장 + 프롬프트 전체가 입력 **5,374~5,615 토큰**(출력 641~802)으로, §5의 분할 호출 기준(20만 토큰)의 3% 미만이다(D-3). 분할 호출은 구현하지 않았다.

## 10. 프로덕션 전환 검증 (`ubidict-py/`)

`test/`에서 검증된 로직을 FastAPI 서비스로 옮긴 뒤, **포팅이 로직을 깨뜨리지 않았는지**부터 확인했다.

| 검증 | 방법 | 결과 |
|---|---|---|
| 포팅 회귀 | `test/fixtures`를 그대로 HTTP 요청으로 변환해 `/extract`·`/contrast` 호출 | extract 15개 후보, contrast 23개 제안 — `구독자→이용자` 등 골드셋과 일치 |
| 컨테이너 | `docker build` + 컨테이너에서 `/health` | 성공 |
| 큐 E2E (09-13) | 실제 AWS SQS(`lovebug-llm-request`/`-reply`)에 가짜 백엔드가 발행 → 컨슈머 수신 → 실제 Gemini → 응답 큐 | extract 5.2s / contrast 2.7s, 왕복 성공 |
| 멱등성 | 같은 `jobId`를 다시 발행 | Gemini 재호출 없이 스킵, `processed_jobs`에 기록 확인 |
| DB 직접 조회 (09-14) | 실제 백엔드 MySQL에 테스트 행을 넣고 `/jobs/extract`·`/jobs/contrast` | stub 모드 2.5초 빈 결과 / real 모드 extract 5.5s·contrast 5.1s 성공 |
| 단위 테스트 | boto3·pymysql·Gemini 전부 모킹 | 23개 통과 |
| CI | GitHub Actions(ruff + pytest) | 실제 push로 통과 확인 |

**Gemini·SQS·MySQL을 실제로 부르는 테스트는 CI에 올리지 않았다** — 비용과 비결정성 때문이다. 그 경로는 사람이 실제 인프라로 수동 검증했고, CI는 모킹된 분기 로직만 회귀 테스트한다.

## 12. 아직 측정하지 못한 것

- **실제 팀 문서에서의 성능.** 픽스처는 함정을 의도적으로 심은 합성 문서다. 특히 VARIANT는 마크다운 강조(`**볼드**`)에 의존하므로 평문 문서에서는 빈 결과가 나올 수 있다(D-8).
- **`3.7`·`3.8-flash`.** 이틀에 걸쳐 5회 시도했으나 전부 `503`으로 측정 자체가 불가능했다.
- **사전집 수백 개 규모.** 현재 13개 기준 측정이다. 사고 유도 스키마는 사전집 크기에 비례해 토큰이 늘고, 수백 개에서는 오히려 재현율이 떨어질 수 있다(D-29).
- **5xx 상황에서의 키 순회.** 실제 503을 강제로 만들 방법이 없어 코드 경로 확인으로만 검증했다(D-40).
- **진짜 백엔드와의 연동.** 큐 E2E는 가짜 백엔드(`scripts/stub_backend.py`)로 했다 — 백엔드 쪽 요청 기능이 아직 미구현이다.
