# [수동 사용] Gemini로 §12 대조 테스트용 문서 생성 — 검증용

> **이 프롬프트는 앱 코드가 읽지 않는다.** `app/pipeline/`이 자동으로 호출하는 `contrast_01_role.md`~`contrast_04_input.md`와 다르다 — 이건 **사람이 Gemini(AI Studio·Gemini 앱 등)에 직접 붙여넣어** 새 검증용 문서를 만들 때 쓰는 프롬프트다.
>
> **왜 필요한가.** 지금 `fixtures/contrast/docs/9월_CS_이슈_노트.md`는 사람이 직접 써서, 어떤 문장에 어떤 정답·함정을 심을지 이미 다 알고 쓴 문서다 — "이미 답을 알고 만든 시험"이라 규칙/LLM 단계가 정말 일반화되는지 보여주지 못한다. 이 프롬프트로 Gemini가 **스스로 어떤 표현을 쓸지 고르게** 만들면, 그 결과를 새 검증용 문서로 써서 지금 파이프라인이 미리 짜맞춘 정답이 아니어도 실제로 찾아내는지 볼 수 있다.
>
> **이후 처리는 사람이 한다.** Gemini가 만든 문서를 그대로 `fixtures/contrast/`에 반영하지 않는다 — 결과를 검토한 뒤 어떻게 쓸지(새 문서로 추가할지, `gold.csv`에 어떤 행을 새로 적을지)는 사람이 판단한다(AGENTS.md "골드셋은 사람이 판단" 원칙). 지금 있는 `9월_CS_이슈_노트.md`(19개 절, 골드셋 25개 커버)는 회귀 기준선으로 그대로 둔다 — 이 프롬프트로 만든 문서는 **별도의 추가 검증용**이다.
>
> **사용법.** 아래 "===== 프롬프트 시작 =====" 부터 "===== 프롬프트 끝 =====" 까지를 그대로 복사해 Gemini에 붙여넣는다. 사전집(아래 JSON)은 이미 프롬프트 안에 포함돼 있다 — `fixtures/contrast/dictionary.json`의 `dictionary` 배열과 100% 동일하다. 사전집이 바뀌면(용어 추가·정의 수정) 이 프롬프트의 JSON 블록도 그만큼 갱신해야 한다.

## 네가 할 일

**사내 문서 1개**를 새로 써라. 장르는 네가 정해라 — 예: CS 이슈 노트, 부서 회의록, 운영 점검 리포트, 신규 기획 초안 등 이 회사에 실제로 있을 법한 것이면 무엇이든 좋다. 제목·작성 부서·날짜를 스스로 정해서 문서 맨 위에 적어라.

문서를 쓰면서 위 사전집의 개념들 중 일부(전부일 필요 없다)를 **자연스럽게** 다뤄라. 이때 각 개념마다 아래 두 방식 중 **어느 쪽을 쓸지 네가 자유롭게 골라라**:

- **동의어 그대로**: `synonyms`에 있는 표기를 문장에 그대로 써라
- **정의만 풀어서**: `synonyms`의 표기는 하나도 안 쓰고, `definition`이 가리키는 개념을 다른 말로 설명하는 문장을 써라 (예를 들지 않을 테니 네가 자연스러운 업무 문체로 직접 표현을 골라라)

그리고 이 회사에 있을 법하지만 **사전집에는 없는** 다른 개념들도 몇 개 자연스럽게 섞어 넣어라 — 결제 취소, 환불, 반품, 관리자·운영자 권한, 공지·알림, 구독 갱신·연장, 콘텐츠 등급, 주문 처리 같은 것들이 그 예다(이 목록에 얽매이지 말고 네가 생각하기에 이 회사에 실제로 있을 법한 다른 개념을 자유롭게 추가해도 좋다).

## 절대 하지 말 것

- **정의 문장을 그대로 옮겨 적지 마라.** "정의만 풀어서" 방식을 쓸 때도 위 JSON의 `definition` 문구를 그대로 베끼지 말고, 실제 업무 상황(예: 특정 고객 사례, 특정 날짜의 이슈)처럼 완전히 다른 문장으로 표현해라. 정의를 그대로 반복하면 너무 쉬운 문제가 된다.
- **어떤 문장이 정답이고 어떤 게 함정인지 문서 안에서 표시하지 마라.** 굵게 강조하거나, 밑줄 긋거나, "※ 주의" 같은 표시를 달지 마라 — 실제 사내 문서처럼 아무 표시 없이 자연스럽게 섞여 있어야 한다.
- **모든 사전집 항목을 억지로 다 넣으려 하지 마라.** 실제 문서라면 어떤 개념은 아예 안 나올 수도 있다. 자연스러움이 커버리지보다 중요하다.
- **길이는 실제 사내 문서 수준으로** — 너무 짧게 3~4문장으로 끝내지 말고, 여러 절(소제목)로 나눠 충분히 길게 써라.

## 출력 형식 — 반드시 아래 두 부분으로 나눠 응답하라

### 1부: 문서 본문

```
# (제목)

작성: (부서) · (날짜)

## 1. (소제목)
(본문)

## 2. (소제목)
(본문)
... (필요한 만큼)
```

### 2부: 자체 보고 (문서 본문 다음에, 구분선 `---` 아래에 이어서)

**표 A — 사전집 개념을 실제로 어디에 어떻게 담았는지** (다룬 것만, 표 형식):

| termId | 문서에 실제로 쓴 문장(그대로 인용) | 방식(동의어 그대로 / 정의만 풀어서) |
|---|---|---|

**표 B — 사전집에 없는 개념을 어디에 넣었는지** (표 형식):

| 실제로 쓴 문장(그대로 인용) | 그 개념이 뭔지 한 줄 설명 |
|---|---|

이 두 표는 채점 기준(`gold.csv`)을 사람이 새로 작성할 때 참고용으로만 쓴다 — 정답 그 자체로 자동 채택되지 않으니 정직하게, 실제로 쓴 그대로 보고해라.

## 결과를 받은 뒤 (사람이 할 일)

1. 1부(문서 본문)를 읽고 어색하거나 문제(예: 여전히 정의를 베낀 문장)가 있으면 이 프롬프트를 조정해 다시 생성하거나 직접 손본다.
2. 2부(자체 보고)를 **그대로 믿지 말고** 실제 문서와 대조해 확인한다 — LLM이 문구를 살짝 다르게 인용하거나 놓친 것이 있을 수 있다.
3. 확인이 끝나면:
   - 문서를 `fixtures/contrast/docs/`에 새 파일로 추가하고 `dictionary.json`의 `documents`에 메타를 등록한다
   - `gold.csv`에 새 행을 추가한다 — 표 A는 `expected_method`(동의어 그대로→`rule`, 정의만 풀어서→`llm`)·`expected_text`(rule만) 판단에, 표 B는 트랩(`N-*`) 후보 판단에 쓴다
   - 기존 `9월_CS_이슈_노트.md`·그 gold 행은 그대로 둔다 — 이 새 문서는 회귀 기준선에 **추가**되는 것이지 대체가 아니다
4. `python -m app.cli contrast --fixtures fixtures/contrast ...`로 돌려 새 문서에서도 파이프라인이 실제로 찾아내는지 확인한다.
